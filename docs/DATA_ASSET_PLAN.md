# ROUNDI 데이터 자산 설계안 (승인 전 · 구현 안 함)

> 작성 2026-11-20. **이 문서는 설계 보고서이며, DB·코드는 아직 아무것도 바꾸지 않았다.**
> 대표 승인 없이 기존 기능 삭제·대규모 구조 변경 금지. 아래 모든 변경은 "추가만" 하는 방식으로 설계했다.

## 0. 현재 시스템 분석 (2026-11-20 기준, 마이그레이션 27개 · 테이블 26개)

### 이미 쌓이고 있는 자산 (좋은 점)

- 쓰기는 모두 SECURITY DEFINER 함수로만, 테이블 직접 쓰기 권한 없음 (`01_schema_security` 검사).
- 개인정보는 `profile_private`에 분리, 탈퇴 시 익명화.
- 실결제 차단(`mode = 'test'`).

## ① 현재 구조의 문제점 (분석 관점)

| # | 문제 | 영향 |
|---|---|---|
| 1 | **행동 기록이 전혀 없음.** 노출, 조회, 체류, 클릭, 검색어를 저장하지 않음. "최근 본 글"은 브라우저(localStorage)에만 있음 | 전환율(조회 → 신청)을 계산할 수 없음. "관심은 높은데 공급이 없는" 것을 찾을 수 없음 |
| 2 | **상태를 덮어쓰는 구조.** `bookings.status` 한 칸이 신청 → 취소로 바뀌면 중간 과정이 사라짐. 결제창에서 그만둔 것, 정원 초과로 실패한 신청 시도는 남지 않음 | 예약 퍼널의 이탈 지점을 알 수 없음 |
| 3 | **저장·팔로우 해제 시 행이 삭제됨** (`saved_meetups`, `host_follows`) | "저장했다가 취소" 이력이 사라짐 |
| 4 | **비로그인 저장은 브라우저에만 저장됨** | 비로그인 관심도가 서버에 안 남음 |
| 5 | **태그·주제 필드가 없음.** 분야(`category_slug`) 하나뿐 | "필름 사진", "브랜딩"처럼 세부 주제별 분석 불가 |
| 6 | **지역이 자유 입력**(`meetup_sessions.area`: "성수" / "성수동" / "성동구 성수동") | 지역별 수요 집계가 흩어짐 |
| 7 | **유입 경로 기록 없음** (어디서 왔는지, 공유 링크, 광고 등) | 추천·공유 효과를 측정할 수 없음 |
| 8 | **테스트 데이터 섞임.** 자동 테스트(E2E) 계정, 샘플, 관리자 본인의 행동이 실제 데이터와 섞임 | 숫자가 부풀려짐 |
| 9 | **관리자 통계를 매번 즉석 계산** (`admin_overview` 등) | 데이터가 커지면 느려짐 |
| 10 | **개인정보 처리방침에 "이용 기록·행동 분석" 항목이 없음** | 이 상태로 행동 수집을 시작하면 안 됨 (먼저 고지·동의 필요) |

## ② 추가할 데이터베이스 구조

### 설계 원칙
1. **기존 테이블은 삭제·변경하지 않는다.** 새 `analytics` 스키마를 따로 만든다 (API로 노출하지 않음 → `public`의 보안 검사 목록은 그대로).
2. **분석 데이터에는 실명·이메일·전화번호를 넣지 않는다.** 회원 ID 대신 **분석용 가명 ID**만 쓴다.
3. **원천 기록(이벤트)은 추가만 한다(append-only).** 고치거나 지우지 않고, 보존 기간이 지나면 통째로 정리한다.
4. **화면은 집계 테이블에서만 읽는다.** 원천 기록을 매번 계산하지 않는다.

### 전체 그림

```
[사이트 화면]──(노출·조회·클릭·검색)──▶ /api/e (검사·중복 제거) ─┐
                                                              ├─▶ analytics.events (원천 기록, 월별 분할)
[DB 함수: 신청·결제·취소·환불·출석·후기·저장]──(트리거)───────────┘          │
                                                                    (매시간 pg_cron)
                                                                          ▼
                                    analytics.daily_* (일별 집계) ──▶ 관리자 분석 화면
private.analytics_subjects (회원 ID ↔ 가명 ID, 탈퇴 시 삭제 → 연결 끊김)
```

### 새 테이블

| 테이블 | 위치 | 역할 |
|---|---|---|
| `private.analytics_subjects` | private | 회원 ID ↔ **분석용 가명 ID** 대응표. 관리자 화면에서도 안 보임. **탈퇴 시 삭제** → 이후 분석 기록은 누구 것인지 알 수 없게 됨 |
| `analytics.event_types` | analytics | **이벤트 사전.** 허용된 이벤트 이름, 필수 속성, 버전. 사전에 없는 이벤트는 거부 |
| `analytics.events` | analytics | **원천 행동 기록** (월별 파티션). 아래 구조 참고 |
| `analytics.ingest_rejects` | analytics | 거부된 이벤트 수 (이유별 일별 집계만, 내용은 저장 안 함). 데이터 품질 확인용 |
| `analytics.daily_meetup_stats` | analytics | 날짜 × 프로그램: 노출, 조회, 고유 조회자, 평균 체류, 저장, 신청 시도, 신청, 결제, 취소, 환불, 매출 |
| `analytics.daily_category_stats` | analytics | 날짜 × 분야: 같은 지표 + 열린 일정 수, 남은 자리 (공급) |
| `analytics.daily_host_stats` | analytics | 날짜 × 호스트: 판매, 매출, 순수익, 재참여, 평점 |
| `analytics.daily_demand` | analytics | 날짜 × 지역 × 요일 × 시간대 × 가격대: 조회, 저장, 대기, 신청 |
| `analytics.daily_search_terms` | analytics | 날짜 × 정규화된 검색어: 검색 수, **결과 0건 수** (공급 부족 신호). 5회 미만 검색어는 저장하지 않음 |
| `public.tags`, `public.meetup_tags` | public | 주제 태그 (함수로만 쓰기, 관리자가 정리) |
| `public.areas` | public | 지역 사전 (권역 → 구 → 동). `meetup_sessions`에 **빈 값 허용 열 `area_code`를 추가만** 함. 기존 `area`는 그대로 |

### `analytics.events` 구조 (안)

```sql
create table analytics.events (
  id            bigint generated always as identity,
  event_id      uuid        not null,            -- 화면/서버가 만든 고유값 → 중복 방지
  event_name    text        not null,            -- event_types 에 있는 이름만
  schema_ver    smallint    not null default 1,
  source        text        not null check (source in ('client','server')),
  occurred_at   timestamptz not null,            -- 발생 시각 (미래·7일 이전은 거부)
  received_at   timestamptz not null default now(),
  subject_id    uuid,                            -- 분석용 가명 ID (로그인 시), 회원 ID 아님
  visitor_id    uuid,                            -- 브라우저 무작위 ID (분석 동의 시에만)
  visit_id      uuid,                            -- 한 번 방문(30분 무활동이면 새 방문)
  meetup_id     uuid,  session_id uuid,  host_id uuid,  content_id uuid,
  category_slug text,
  surface       text,                            -- home / list / search / detail / host / journal ...
  position      smallint,                        -- 목록에서 몇 번째에 보였는지
  props         jsonb       not null default '{}', -- 사전에 정의된 키만 (금액, 이유 코드, 체류 초 등)
  referrer_host text,                            -- 유입 도메인만 (전체 주소 저장 안 함)
  utm_source text, utm_medium text, utm_campaign text,
  device        text check (device in ('mobile','tablet','desktop')),
  is_internal   boolean     not null default false, -- 관리자·테스트·샘플 → 분석에서 기본 제외
  primary key (id, occurred_at),
  unique (event_id, occurred_at)
) partition by range (occurred_at);
```

**저장하지 않는 것:** IP 주소, 전체 User-Agent, 이메일, 닉네임, 전화번호, 검색어 원문(정규화 후 집계만), 후기 본문, 정확한 위치.

### 중복·잘못된 데이터 방지

| 문제 | 막는 방법 |
|---|---|
| 같은 이벤트가 두 번 들어옴 (새로고침, 재전송) | `event_id` 고유 제약 → 두 번째는 무시 |
| 같은 사람이 같은 프로그램을 계속 새로고침 | 조회는 **같은 방문자 × 같은 프로그램 × 30분 안**에는 1번만 집계 |
| 이상한 이름·속성 | `event_types` 사전과 속성 검사. 통과 못 하면 거부하고 `ingest_rejects`에 개수만 기록 |
| 시각 조작 | 미래 시각, 7일보다 오래된 시각은 거부 |
| 봇, 대량 전송 | 한 번에 최대 20개, 방문자당 분당 한도, 봇 User-Agent 제외 |
| 결제·신청 숫자 조작 | **돈과 관련된 이벤트(신청 확정·결제·취소·환불·출석·후기)는 화면이 아니라 DB 트리거만 기록**. 화면에서 보낸 같은 이름은 거부 |
| 테스트·관리자 데이터 | `is_internal = true`로 표시. 분석 화면은 기본으로 제외 |

### 개인정보와 동의

| 항목 | 설계 |
|---|---|
| 동의 | `consent_type`에 `analytics`(행동 분석) 값을 **추가만** 함. 가입 시 선택, 마이페이지에서 언제든 끄기 |
| 비로그인 | 브라우저 무작위 ID는 동의 배너에서 허용했을 때만 생성. 거부하면 ID 없이 **익명 집계(조회 수 등)만** |
| 처리방침 | "이용 기록·행동 분석" 항목, 보존 기간, 거부 방법을 추가 (**수집 시작 전에**, 법률 검토 필요) |
| 분리 | 분석 기록에는 가명 ID만. 회원 ID 대응표는 `private`에, 운영팀 화면에서도 조회 불가 |
| 탈퇴 | 대응표 삭제 → 남은 분석 기록은 누구 것인지 알 수 없는 통계 자료가 됨 |
| 보존 | 원천 기록 **13개월** 후 월 단위로 삭제(pg_cron). 일별 집계는 계속 보관 |
| 접근 | 관리자 + 2단계 인증만. 내보내기(다운로드) 시 감사 기록. **5명 미만 집단은 숫자를 가림** (특정인 추정 방지) |

## ③ 수집할 행동 이벤트

**출처**: 화면 = 브라우저에서 전송 (동의 필요, 일부 누락 가능) · 서버 = DB 트리거 (정확, 돈과 관련된 진실)

| 단계 | 이벤트 | 출처 | 주요 속성 |
|---|---|---|---|
| 유입 | `visit_start` | 화면 | 유입 도메인, utm, 기기, 첫 방문 여부 |
| 노출 | `program_impression` | 화면 | 프로그램, 위치(surface, position). 화면에 50% 이상 1초 보였을 때만 |
| 조회 | `program_view` | 화면 | 프로그램, 어디서 왔는지(surface) |
| 체류 | `program_dwell` | 화면 | 체류 초(구간), 스크롤 깊이(25/50/75/100%). 페이지를 떠날 때 1번 |
| 클릭 | `program_click` | 화면 | 대상: 신청 버튼, 일정 선택, 크리에이터, 공유, 캘린더, 길찾기, 후기 더보기 |
| 검색 | `search` | 화면 | 정규화 검색어, 결과 수 (원문 저장 안 함) |
| 필터 | `filter_apply` | 화면 | 대분류, 분야, 지역 |
| 저장 | `save`, `unsave` | 서버 | 프로그램 (해제 이력도 남음 → 문제 3 해결) |
| 팔로우 | `follow`, `unfollow` | 서버 | 호스트 |
| 대기 | `waitlist_join`, `waitlist_leave` | 서버 | 일정 |
| 예약 시도 | `booking_attempt` | 서버 | 일정, 인원, 결과(성공 / 정원 초과 / 이미 신청 / 기타 이유 코드) |
| 결제 | `checkout_view` | 화면 | 결제 화면 진입 |
| 결제 | `payment_paid`, `payment_failed`, `payment_expired` | 서버 | 금액, 쿠폰 여부 |
| 확정 | `booking_confirmed` | 서버 | 무료·유료, 금액, 처음 신청인지 재참여인지 |
| 취소 | `booking_cancelled` | 서버 | 누가(참가자/호스트), 프로그램 며칠 전 |
| 환불 | `refund` | 서버 | 환불 비율, 금액 |
| 참여 | `attendance_marked` | 서버 | 참석/불참 |
| 후기 | `review_written` | 서버 | 별점 (본문 없음) |
| 재참여 | (계산) | 집계 | 같은 사람의 두 번째 이후 확정 → `booking_confirmed.props.repeat` |
| 추천 | `share_click` (화면), `referral_landing` (화면) | 화면 | 공유 수단, 공유 링크로 들어온 방문 (추천 링크 기능은 보류 중 → 지금은 utm만) |
| 콘텐츠 | `content_view`, `content_to_program_click` | 화면 | 저널 글 → 프로그램 이동 |
| 알림 | `notification_click` | 화면 | 알림 종류 |

**과거 데이터 채우기:** 신청·결제·취소·환불·후기·저장·팔로우는 기존 테이블에 시각이 있으므로 **한 번 복사해서** 출시 이후 서버 이벤트를 채울 수 있다. 조회·노출 같은 화면 이벤트는 과거분을 만들 수 없다.

## ④ 관리자 분석 화면 (`/admin/analytics`, 시안 승인 후 제작)

공통: 기간 선택(7일/30일/90일/직접), 대분류 필터, "테스트 제외"(기본 켜짐), 표본이 적으면 "표본 적음" 표시, 5명 미만 집단은 가림.

| 탭 | 보여 주는 것 | 계산 방법 |
|---|---|---|
| **개요** | 방문자, 상세 조회, 신청, 결제, 매출, 전환율, 재참여율 + 지난 기간 대비 | 전환율 = 확정 신청한 고유 사람 ÷ 상세를 본 고유 사람 |
| **인기 콘텐츠** | 순위표: 조회, 저장, 신청, 결제, 전환율, 평점 | 기본 정렬 = 확정 신청 수, 동점은 저장 수 |
| **카테고리 퍼널** | 분야별 노출 → 조회 → 신청 시도 → 결제 → 참석 → 후기 단계 막대 | 단계별 이탈률 |
| **가격대** | 무료 / ~2만 / 2~4만 / 4~6만 / 6~10만 / 10만+ 구간별 신청 수, 전환율 | 신청 당시 단가 기준 |
| **지역·요일 수요** | 지역 × 요일 표(색 진하기로 많고 적음), 시간대별 막대 | 조회·저장·신청 합산 |
| **성장 중** | 최근 14일이 그 전 14일보다 조회·신청이 크게 는 프로그램·분야 | 증가율 + 최소 표본 조건 |
| **공급 부족** | 관심은 높은데 공급이 적은 분야·지역·시간대 | 수요 신호(조회 + 저장 + 대기 + 결과 0건 검색) ÷ 열린 자리 수 |
| **호스트 성과** | 호스트별 판매, 매출, 순수익, 재참여율, 평점, 월별 추이 | 정산 테이블 + 집계 |
| **데이터 품질** | 이벤트 수신량, 거부 수(이유별), 중복 차단 수, 마지막 집계 시각 | 문제 조기 발견 |

나중에(별도 승인): 호스트에게 **자기 프로그램 통계만** 보여 주는 "내 성과" 화면.

## ⑤ 구현 순서와 예상 위험

| 단계 | 내용 | 기존 기능 영향 |
|---|---|---|
| 0 | **승인** + 개인정보 처리방침 개정안 + 법률 확인 | 없음 |
| 1 | `analytics` 스키마, 이벤트 사전, 가명 ID, 수집 함수, 보안 테스트(pgTAP) | 없음 (새 스키마만) |
| 2 | 서버 이벤트 트리거 (신청·결제·취소·환불·출석·후기·저장·팔로우·대기) + 과거 데이터 1회 채우기 | 기존 쓰기에 트리거가 붙음 → **실패해도 원래 동작은 계속되게** 예외 처리 |
| 3 | 화면 수집기(작은 스크립트) + `/api/e` + 분석 동의 설정 | 화면에 동의 배너 추가 |
| 4 | 태그·지역 사전 (빈 값 허용 열 추가만), 관리자 정리 화면 | 기존 입력은 그대로 |
| 5 | 일별 집계 + pg_cron (매시간, 다시 돌려도 같은 결과) | 없음 |
| 6 | 관리자 분석 화면 (**시안 먼저**) | 관리자 메뉴 1개 추가 |
| 7 | 보존 기간 정리, 데이터 품질 화면 | 없음 |

각 단계마다 로컬 전체 검사(타입, 린트, 단위, 통합, pgTAP, E2E) → 스테이징 배포(대표 승인) 순서로 진행.

### 예상 위험

| 위험 | 대응 |
|---|---|
| 트리거 오류로 신청·결제가 실패 | 트리거 안에서 오류를 삼키고 원래 처리는 계속. 테스트로 확인 |
| 데이터가 빠르게 커짐 | 월별 파티션, 13개월 후 삭제, 화면은 집계 테이블만 조회, 인덱스 최소화 |
| 개인정보 문제 | 처리방침 개정 전 수집 금지, 동의 관리, 가명 ID, 소수 집단 가림, 법률 검토 |
| 광고 차단기·동의 거부로 화면 이벤트 누락 | 돈과 관련된 핵심 지표는 서버 이벤트로 계산. 화면 이벤트는 "추세"로 해석 |
| 테스트 데이터가 숫자를 부풀림 | `is_internal` 표시 + 기본 제외. E2E 계정 식별 규칙 필요 |
| 초기 데이터가 적어 결론이 흔들림 | "표본 적음" 표시, 최소 표본 조건 |
| 사이트 속도 저하 | 수집기는 화면 표시 후 늦게 로드, 묶어서 전송(sendBeacon), 정적 페이지를 동적으로 바꾸지 않음 |
| 저장 비용 | Supabase 요금제 용량 확인. 출시 초기 규모에서는 문제없을 것으로 예상하지만 실제 수치로 점검 |

### 대표가 정해야 할 것
1. 분석 동의 방식: **선택 동의(권장)** / 고지 후 거부 방식
2. 원천 기록 보존 기간: **13개월(권장)** / 다른 기간
3. 태그 입력: 호스트가 고르고 관리자가 정리(권장) / 관리자만
4. 구현 범위: 1~2단계(서버 이벤트)부터 먼저(권장) / 1~7단계 전체
