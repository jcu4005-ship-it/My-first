## 1. 사업 분석과 개발 요구사항

### 1-1. 사업 구조를 시스템 관점에서 다시 보면

이 플랫폼은 **양면 마켓플레이스**(쉬운 설명: 파는 사람과 사는 사람을 연결하고 중간에서 수수료를 받는 장터)입니다.
시스템이 반드시 잘해야 하는 것은 딱 세 가지입니다.

1. **신뢰** — 결제한 돈이 정확히 기록되고, 환불·정산이 틀리지 않는다.
2. **공급(호스트) 확보** — 호스트가 모임을 쉽게 만들고, 운영하고, 돈을 받을 수 있다.
3. **수요(참가자) 전환** — 모임을 보고 3번 이내의 터치로 예약까지 간다.

차별점 4가지(호스트 육성·호스트 네트워크·참가자 연결·콘텐츠 지원)는 **위 3가지가 먼저 작동해야 의미가 있습니다.**
그래서 MVP에서는 차별점을 "데이터 구조는 미리 준비하되, 기능은 가볍게" 넣는 전략을 제안합니다.

### 1-2. 기능 요구사항 (요약)

**참가자**
- 회원가입/로그인(이메일 + 카카오 제안), 프로필(닉네임, 사진, 관심사)
- 모임 탐색: 카테고리, 날짜, 지역, 가격, 검색어 / 상세 페이지
- 예약·결제, 예약 내역, 취소·환불 신청(정책에 따라 환불액 자동 계산)
- 참여 완료 후 후기·평점(참석 확인된 사람만)
- 호스트 팔로우, 모임 저장(찜)

**호스트**
- 호스트 신청 → 관리자 승인
- 모임 개설(임시저장 → 검수 요청 → 공개), 수정, 회차(날짜) 추가
- 참가자 목록·예약 현황, 출석 체크, 공지 작성
- 매출·수수료·정산 내역 확인, 정산 계좌 등록
- (후속) 다른 호스트에게 공동 모임 제안

**관리자**
- 회원·호스트·모임 관리(승인/반려/정지)
- 예약·결제·환불 내역 조회 및 처리
- 수수료 등급과 수수료율 설정
- 정산 생성·확정·지급 완료 처리
- 후기·신고 처리, 전체 통계

### 1-3. 비기능 요구사항 (기능은 아니지만 꼭 지켜야 할 품질 기준)

| 구분 | 기준 |
|---|---|
| 보안 | 모든 데이터 접근은 DB 단에서 권한 재검증(RLS). 비밀키는 환경변수에만 |
| 정합성 | 정원 초과 예약 0건, 중복 결제 0건. 금액은 서버가 계산 |
| 추적성 | 돈이 움직인 모든 기록은 수정·삭제하지 않고 **추가만** 한다(원장 방식) |
| 성능 | 모바일 4G 기준 첫 화면 2.5초 이내 목표, 이미지 자동 최적화 |
| 개인정보 | 최소 수집, 호스트에게는 확정 참가자의 필요한 정보만 노출 |
| 운영 | 테스트 환경과 운영 환경 분리(DB·결제키 모두 별도) |
| 접근성 | 모바일 우선, 글자 대비·버튼 크기 기준 준수 |

### 1-4. 설계 전에 짚어야 할 사업적 포인트 (중요)

1. **돈의 흐름과 법적 구조** — 참가자 결제금을 플랫폼이 받았다가 호스트에게 나눠주는 구조는, 국내에서는 PG사의 **오픈마켓/정산대행(지급대행) 상품** 계약이 필요하거나 전자금융 관련 규제 검토가 필요할 수 있습니다. 개발로 해결되는 문제가 아니라 **PG사·법률 자문 확인 사항**입니다. 시스템은 어느 쪽이든 대응할 수 있게 설계합니다.
2. **통신판매중개업자 고지** — 플랫폼이 판매 당사자가 아니라 중개자라면 그 사실과 호스트(판매자) 정보를 화면에 고지해야 합니다(전자상거래법).
3. **호스트 소득 세금** — 개인 호스트에게 지급 시 원천징수(예: 사업소득 3.3%) 여부 등은 세무 자문이 필요합니다. DB에는 "세금 공제액" 칸을 미리 둡니다.
4. **주류가 포함된 모임(와인 등)** — 주류 판매·제공 방식과 미성년자 참여 제한 정책이 필요합니다.

## 2. 시스템 아키텍처

### 2-1. 전체 그림

```
 [참가자/호스트/관리자의 휴대폰·PC 브라우저]
                 │  (HTTPS 암호화 통신)
                 ▼
 ┌─────────────────────────────────────────────┐
 │  Vercel  (웹사이트를 실제로 띄워주는 서버)       │
 │  Next.js 앱                                   │
 │   ├─ 화면(페이지)                               │
 │   ├─ 서버 액션 / API  ← 예약·결제·환불 등 중요한 처리 │
 │   └─ 결제 웹훅 수신 창구 ← PG사가 결제결과를 알려주는 곳│
 └───────┬───────────────────────┬─────────────┘
         │                       │ (서버끼리 비밀키로 통신)
         ▼                       ▼
 ┌──────────────────┐     ┌──────────────────┐
 │ Supabase          │     │ PG사 (토스/포트원) │
 │  ├ PostgreSQL DB  │     │  테스트/운영 분리   │
 │  │  + RLS(권한규칙) │     └──────────────────┘
 │  ├ Auth (로그인)   │
 │  ├ Storage (사진)  │     ┌──────────────────┐
 │  └ 예약 마감 등 예약작업│     │ 이메일/알림 발송   │
 └──────────────────┘     │ (Resend 등, 후속:알림톡)│
                          └──────────────────┘
```

### 2-2. 각 구성요소의 역할 (쉬운 설명)

| 구성요소 | 비유 | 하는 일 |
|---|---|---|
| **Next.js** | 매장 인테리어 + 카운터 | 화면을 보여주고, 중요한 처리는 서버 쪽 코드로 실행 |
| **Supabase PostgreSQL** | 금고 겸 장부 | 회원, 모임, 예약, 결제 등 모든 데이터 저장 |
| **RLS** (행 단위 보안) | 장부의 줄마다 붙은 자물쇠 | "이 줄은 본인만 / 이 모임 호스트만 / 관리자만 볼 수 있음"을 DB가 직접 검사 |
| **Supabase Auth** | 출입증 발급처 | 회원가입·로그인·비밀번호 재설정·카카오 로그인 |
| **Supabase Storage** | 사진 창고 | 모임 사진, 프로필 사진 저장. 창고에도 권한 규칙 적용 |
| **PG사** | 카드 단말기 회사 | 실제 카드 결제와 취소 처리 |
| **웹훅** | PG사가 거는 확인 전화 | 결제 성공/취소를 PG사가 우리 서버에 직접 알려줌 → 위조 방지 |
| **Vercel** | 건물 임대 | 코드를 올리면 자동으로 웹사이트 배포. 미리보기 주소 제공 |

### 2-3. 환경 분리

| 환경 | 용도 | DB | 결제 |
|---|---|---|---|
| 로컬(개발자 PC) | 개발 | 로컬 Supabase | PG 테스트 키 |
| 스테이징(staging) | 출시 전 점검, 창업자님 검수용 | 별도 Supabase 프로젝트 | PG 테스트 키 |
| 운영(production) | 실제 서비스 | 별도 Supabase 프로젝트 | PG 실제 키 |

- 비밀키는 Vercel/Supabase 대시보드의 **환경변수**에만 저장하고 코드·GitHub에는 절대 올리지 않습니다.
- `.env.example` 파일에 "어떤 키가 필요한지 이름만" 적어 둡니다.

### 2-4. 코드 구조(폴더) 예정안


## 3. 데이터베이스 설계

### 3-1. 핵심 개념: "모임"과 "회차"를 분리

같은 와인 모임을 매주 토요일 연다면, 소개글·사진은 같고 날짜와 정원만 다릅니다.
- **모임(meetup)**: 제목, 설명, 사진, 가격, 정책 등 "상품 정보"
- **회차(session)**: 날짜·시간, 장소, 정원, 현재 예약 인원 등 "한 번의 실제 진행"

MVP에서는 화면상 "모임 1개 = 회차 1개"로 단순하게 보여도, DB는 처음부터 분리해 두면 나중에 반복 모임을 추가할 때 데이터를 갈아엎지 않아도 됩니다.

### 3-2. 테이블 관계도 (요약)

```
users(로그인 계정, Supabase 관리)
  └─1:1─ profiles(회원 프로필)
            ├─1:1─ host_profiles(호스트 정보, 등급, 승인상태)
            │         ├─1:N─ meetups(모임)
            │         │        ├─1:N─ meetup_images(사진)
            │         │        ├─1:N─ meetup_sessions(회차)
            │         │        │        ├─1:N─ bookings(예약)
            │         │        │        │        ├─1:N─ payments(결제)
            │         │        │        │        │        └─1:N─ refunds(환불)
            │         │        │        │        ├─1:1─ reviews(후기)
            │         │        │        │        └─1:N─ ledger_entries(거래 원장)
            │         │        │        └─1:N─ announcements(공지)
            │         │        └─N:M─ meetup_hosts(공동 호스트, 후속)
            │         ├─1:N─ payout_accounts(정산 계좌)
            │         └─1:N─ settlements(정산서) ─1:N─ settlement_items
            ├─N:M─ follows(호스트 팔로우)
            ├─N:M─ saved_meetups(모임 저장)
            └─1:N─ reports(신고)

commission_tiers(수수료 등급표, 관리자 수정)   categories(카테고리)
coupons ─1:N─ coupon_redemptions(쿠폰 사용)    audit_logs(관리자 행동 기록)
payment_webhook_events(PG 알림 원본 보관)       notifications(알림)
```

### 3-3. 테이블별 상세

> 표기: **PK**=각 줄의 고유번호, **FK**=다른 표를 가리키는 연결고리. 금액은 모두 **원 단위 정수**로 저장(소수점 오차 방지).

#### (1) 회원·권한

**profiles** — 모든 회원
| 컬럼 | 설명 |
|---|---|
| id (PK, FK→users) | 로그인 계정과 동일 번호 |
| nickname, avatar_url, bio | 공개 프로필 |
| phone (비공개) | 예약 연락용. 본인·관리자만 열람 |
| birth_year | 주류 모임 등 나이 제한 확인용(선택) |
| interests | 관심 카테고리 목록 |
| status | active / suspended / withdrawn |
| marketing_agreed_at | 마케팅 수신 동의 시각 |

**user_roles** — 권한 (★ 회원이 스스로 수정 불가)
| 컬럼 | 설명 |
|---|---|
| user_id, role | role = `participant` / `host` / `admin` (복수 보유 가능) |
| granted_by, granted_at | 누가 언제 부여했는지 |

> 왜 별도 표인가: 권한을 프로필 안에 두면 "내 프로필 수정" 기능을 악용해 스스로 관리자가 되는 사고가 날 수 있습니다. 권한 표는 관리자 서버 처리로만 바뀝니다.

**host_profiles** — 호스트
| 컬럼 | 설명 |
|---|---|
| user_id (PK) | |
| display_name, intro, expertise, sns_links, cover_image | 호스트 공개 프로필 |
| status | applied(신청) / approved / rejected / suspended |
| tier_id (FK→commission_tiers) | 수수료 등급 |
| custom_commission_rate | 특정 호스트만 예외 수수료(선택) |
| business_type | 개인 / 개인사업자 / 법인 (세금 처리 구분) |
| approved_by, approved_at | |

**commission_tiers** — 수수료 등급표 (관리자 화면에서 수정)
| code | 이름 | 기본 수수료율 |
|---|---|---|
| new | 신규 호스트 | 30% |
| growing | 성장 호스트 | 25% |
| excellent | 우수 호스트 | 20% |
| partner | 핵심 파트너 | 15% |

> 수수료율은 "%의 100배" 정수(예: 30% → 3000)로 저장해 계산 오차를 없앱니다.
> **결제 시점의 수수료율을 예약에 복사(스냅샷)해 둡니다.** 나중에 등급표를 바꿔도 과거 거래는 변하지 않습니다.

> 왜 원장 방식인가: 은행 통장처럼 "잔액을 고쳐 쓰는" 게 아니라 "입출금 내역을 쌓는" 방식이라, 환불·분쟁이 생겨도 언제 무슨 일이 있었는지 100% 추적할 수 있습니다. 요청하신 "플랫폼 수익, 호스트 정산금, 결제 수수료, 쿠폰 부담액, 환불 금액 구분 기록"이 이 표로 해결됩니다.

**계산 예시** (제안 규칙 — 9장에서 확정 필요)
```
정가 50,000원 / 신규 호스트(수수료 30%) / 플랫폼 부담 쿠폰 5,000원 / PG 수수료 3.3%(가정)

참가자 결제액          = 50,000 − 5,000           = 45,000원
PG 수수료              = 45,000 × 3.3%            =  1,485원
플랫폼 수수료(정가 기준) = 50,000 × 30%             = 15,000원
호스트 정산금           = 50,000 − 15,000          = 35,000원   ← 플랫폼 쿠폰은 호스트에게 영향 없음
플랫폼 순수익           = 15,000 − 5,000 − 1,485   =  8,515원
```
- 호스트 부담 쿠폰이었다면: 수수료 기준액 = 45,000 → 수수료 13,500 / 호스트 31,500.

### 3-4. 중복 예약·중복 결제 방지 설계

| 위험 | 방지 방법 (쉬운 설명) |
|---|---|
| 같은 사람이 같은 회차를 두 번 예약 | DB에 "한 사람은 한 회차에 유효 예약 1개만" 규칙(고유 제약)을 걸어 두 번째는 DB가 거부 |
| 마지막 1자리에 2명이 동시에 결제 | 좌석 확보를 DB 함수 하나에서 처리하며, 그 순간 해당 회차 줄을 **잠금**(먼저 온 사람 처리가 끝날 때까지 대기) → 정원 초과 불가 |
| 결제 버튼 연타 / 네트워크 재시도 | 결제 요청마다 고유 열쇠(idempotency key) → 같은 열쇠는 한 번만 처리 |
| 결제창은 성공, 우리 서버 처리는 실패 | PG 웹훅 + 주기적 대사(對査: PG 기록과 우리 기록 비교) 작업으로 자동 복구 |
| 참가자가 결제 금액을 조작 | 금액은 항상 서버가 DB 가격으로 계산하고, PG 승인 전 "요청 금액 = 서버 계산 금액" 검증 |
| 결제 완료를 위조 | 화면이 "성공"이라고 보내는 정보는 믿지 않고, 서버가 PG사에 직접 조회해 확인한 경우에만 확정 |
| 결제 대기 좌석이 계속 묶임 | 10분 지나면 자동 만료 후 좌석 반환 (DB 예약 작업) |

## 4. 권한 구조

### 4-1. 3중 방어

```
1단계 화면:  권한 없는 버튼·메뉴 숨김         ← 편의용일 뿐, 보안 아님
2단계 서버:  모든 요청에서 "로그인했나? 이 권한이 있나?" 확인
3단계 DB:    RLS 규칙으로 데이터 한 줄 한 줄 접근 검사 ← 최종 방어선
```
1·2단계가 뚫려도 3단계에서 막히도록 설계합니다. 그리고 **3단계가 실제로 막는지 자동 테스트**로 검증합니다.

### 4-2. 권한표

| 데이터/행동 | 비로그인 | 참가자 | 호스트 | 관리자 |
|---|---|---|---|---|
| 공개된 모임·호스트 프로필 보기 | ✅ | ✅ | ✅ | ✅ |
| 검수 전/반려 모임 보기 | ❌ | ❌ | 본인 것만 | ✅ |
| 예약·결제 | ❌ | ✅ | ✅(본인 모임 제외) | ✅ |
| 내 예약 보기·취소 | ❌ | 본인 것만 | 본인 것만 | ✅ |
| 후기 작성 | ❌ | 출석 확인된 본인 예약만 | 〃 | ❌(숨김 처리만) |
| 모임 개설·수정 | ❌ | ❌ | 승인된 호스트, 본인 모임만 | ✅ |
| 모임 공개(검수 통과) | ❌ | ❌ | ❌ | ✅ |
| 참가자 목록 보기 | ❌ | ❌ | 본인 모임의 **확정** 참가자만, 최소 정보 | ✅ |
| 참가자 전화번호 | ❌ | ❌ | 기본 비공개(플랫폼 내 공지로 연락) — 결정 필요 | ✅ |
| 출석 체크·공지 작성 | ❌ | ❌ | 본인 모임만 | ✅ |
| 매출·정산 보기 | ❌ | ❌ | 본인 것만 | ✅ 전체 |
| 정산 계좌 | ❌ | ❌ | 본인 것만(뒤 4자리만 표시) | ✅ |
| 환불 승인(예외 처리) | ❌ | ❌ | 본인 모임 취소만 | ✅ |
| 수수료율 변경, 권한 부여 | ❌ | ❌ | ❌ | ✅ (기록 남음) |
| 원장·정산서 수정 | ❌ | ❌ | ❌ | ❌ 수정 불가(조정 기록 추가만) |

### 4-3. 구현 원칙

- 권한 판단은 `user_roles` 표 기준. 로그인 토큰 안의 회원이 수정할 수 있는 값(user metadata)은 권한 판단에 사용하지 않음.
- 돈·좌석·상태를 바꾸는 작업(예약 생성, 결제 확정, 환불, 정산)은 **DB 함수로만** 실행 가능하게 하고, 일반 사용자에게는 해당 표의 직접 수정 권한을 주지 않음.
- 모든 권한을 무시하는 **서비스 키**(마스터키)는 결제 웹훅 등 꼭 필요한 서버 코드에서만 사용, 브라우저로 절대 전달 안 됨.
- 관리자 계정은 2단계 인증(OTP) 필수 권장.
- 사진 창고(Storage)도 경로별 권한 적용: 모임 사진은 해당 호스트만 업로드, 신분증 등 민감 파일은 관리자만 열람.

| 예약 내역 | `/me/bookings` | 예정/지난/취소 탭, 취소 시 **예상 환불액 미리 표시** |
| 후기 작성 | `/me/bookings/[id]/review` | 별점, 글, 사진 |
| 로그인/가입 | `/login`, `/signup` | 이메일·카카오, 약관·개인정보 동의 |

**호스트** (`/host/...`)
| 화면 | 핵심 요소 |
|---|---|
| 호스트 신청 | 소개, 분야, 예정 모임 아이디어, 약관 |
| 대시보드 | 다가오는 회차, 예약 현황, 이번 달 예상 정산액, 할 일(공지·출석 체크) |
| 모임 개설 | 단계형 입력(기본정보 → 사진 → 일정·장소·정원 → 가격·환불정책 → 미리보기 → 검수 요청), **기획 템플릿** 불러오기 |
| 모임 관리 | 상태별 목록, 회차 추가, 수정 |
| 참가자 관리 | 회차별 확정자 목록, 출석 체크, 공지 발송 |
| 예약 현황 | 예약·취소 추이 |
| 매출·정산 | 거래별 정가·수수료·환불·정산액, 정산서 목록, 계좌 등록 |
| 프로필 관리 | 공개 프로필 편집 |

**관리자** (`/admin/...`) — 대시보드, 회원, 호스트 승인, 모임 검수, 거래(결제·환불), 정산, 수수료 설정, 신고·후기, 쿠폰

> 디자인: 관리자/호스트 화면도 "엑셀 같은 관리툴"이 아니라 같은 브랜드의 타이포그래피·여백을 쓰는 깔끔한 화면으로. 표는 모바일에서 카드형으로 전환.

### 5-2. 핵심 사용자 흐름

**A. 참가자 예약 흐름**
```
홈/목록 → 모임 상세 → [일정 선택] → [예약하기]
  → (비로그인이면 로그인 후 원래 화면 복귀)
  → 결제 페이지: 서버가 좌석 10분 확보 + 금액 계산
  → PG 결제창 → 결제 완료
  → 서버가 PG에 직접 확인 → 예약 확정 → 확정 알림(이메일/사이트 알림)
  → 모임 당일: 호스트가 출석 체크
  → 종료 후 "후기 남기기" 알림 → 후기 작성 → 다른 모임 추천 노출
```

**B. 취소·환불 흐름**
```
예약 내역 → [취소] → 정책에 따른 예상 환불액 표시 → 확인
  → 서버가 환불액 재계산 → PG 취소 요청 → 성공 시 환불 완료 + 원장 기록 + 좌석 반환
  → (PG 오류 시 '환불 처리중' 상태로 두고 관리자 화면에 경고)
```

**C. 호스트 흐름**
```
가입 → 호스트 신청 → 관리자 승인 → 모임 개설(템플릿 활용) → 검수 요청
  → 관리자 검수 → 공개 → 예약 들어옴 → 공지 작성 → 당일 출석 체크
  → 종료 → 정산 기간 마감 → 정산서 확인 → 지급 완료
```

**D. 관리자 흐름**
```
대시보드(오늘 할 일: 호스트 승인 n건, 모임 검수 n건, 환불 이슈 n건, 신고 n건)
  → 각 항목 처리 (모든 처리는 감사 기록에 남음)
  → 정산 주기마다: 정산서 생성 → 검토 → 확정 → 이체 → 지급완료 처리
```

## 6. MVP 범위

> **MVP**(최소 기능 제품): "실제 돈을 받고 실제 모임을 운영할 수 있는 가장 작은 버전". 기능 수보다 **정확성**이 우선입니다.

### 6-1. MVP에 포함 (반드시)

| 영역 | 기능 |
|---|---|
| 회원 | 이메일 가입·로그인, 카카오 로그인, 비밀번호 재설정, 프로필, 약관·개인정보 동의, 탈퇴 |
| 탐색 | 홈, 목록, 카테고리, 검색(제목·태그), 필터(날짜·카테고리·지역), 상세, 호스트 프로필 |
| 예약·결제 | 1인 예약, 좌석 임시 확보, PG 결제(**테스트 모드 완성 → 계약 후 실결제 전환**), 결제 검증, 웹훅, 중복 방지 |
| 취소·환불 | 표준 환불 정책, 환불액 자동 계산, PG 취소 연동, 호스트 취소 시 전액 환불 |
| 후기 | 출석자 후기·평점, 신고 |
| 저장·팔로우 | 모임 저장, 호스트 팔로우 (단순 기능이라 MVP 포함) |
| 호스트 | 신청, 프로필, 모임 개설·수정·검수 요청, 회차 관리, 참가자 목록, 출석 체크, 공지, 매출·정산 내역, 계좌 등록 |
| 관리자 | 회원/호스트/모임 관리, 승인·반려, 결제·환불 조회 및 처리, 수수료 등급 설정, 정산서 생성·확정·지급 기록, 신고 처리, 기본 통계 |
| 돈 기록 | 거래 원장(플랫폼 수익·호스트 정산금·PG 수수료·쿠폰 부담·환불 분리 기록) |
| 알림 | 예약 확정/취소/공지 — 이메일 + 사이트 내 알림 |
| 호스트 육성(가벼운 버전) | 모임 기획 템플릿 3~5종, 운영 가이드 페이지 |
| 법적 필수 | 이용약관, 개인정보처리방침, 통신판매중개 고지, 환불정책 페이지 |

### 6-2. MVP 직후 (2단계)

- 쿠폰 발급·사용(데이터 구조는 MVP에 포함, 화면은 2단계) — *요청 시 MVP로 당길 수 있음*
- 대기자 명단(정원 마감 시 대기 → 취소 발생 시 알림)
- 카카오 알림톡/문자 알림
- 관심사 기반 간단 추천("이 모임 참가자들이 간 다른 모임")
- 반복 회차 일괄 생성
- 호스트 등급 자동 산정(매출·평점 기준 제안 → 관리자 확정)

### 6-3. 나중에 (3단계 이후)

- 호스트 협업: 공동 모임 제안·수락, 수익 배분 정산
- 개인화 추천 고도화
- 콘텐츠 지원: 사진·릴스 촬영 예약, 마케팅 키트 자동 생성
- PG 지급대행 연동 자동 정산, 세금계산서·원천징수 자동화
- 참가자 커뮤니티(모임 후 사진 공유, 채팅)
- 멤버십/정기 구독, 기업(B2B) 모임
- 네이티브 앱

## 8. 개발 순서와 작업 계획

> 각 단계가 끝날 때마다 **스테이징 주소**로 직접 눌러보며 확인하실 수 있게 합니다. 확인 후 다음 단계 진행.

| 단계 | 기간(예상) | 만드는 것 | 완료 기준(확인 방법) |
|---|---|---|---|
| **0. 기반 준비** | 0.5주 | 프로젝트 생성, 폴더 구조, 디자인 기본(색·글꼴·버튼), Supabase·Vercel 연결, 테스트/운영 분리, 자동 검사 | 스테이징 주소에 빈 홈 화면 표시 |
| **1. 회원·권한** | 1주 | 가입·로그인(이메일·카카오), 프로필, 권한 표, RLS 기본, 관리자 계정 | 역할별로 접근 가능한 화면이 다름 + RLS 자동 테스트 통과 |
| **2. 호스트·모임 등록** | 1.5주 | 호스트 신청·승인, 모임 개설(단계형)·사진 업로드·회차, 검수 흐름 | 호스트가 만든 모임이 관리자 승인 후에만 공개 |
| **3. 탐색 화면** | 1.5주 | 홈, 목록, 카테고리, 상세, 호스트 프로필, 검색·필터, 저장·팔로우 | 모바일에서 탐색→상세까지 자연스럽게 이동 |
| **4. 예약·결제** ★ | 2주 | 좌석 확보, 금액 계산, PG 테스트 결제, 결제 검증, 웹훅, 원장 기록, 만료 처리, 확정 알림 | 동시 예약 테스트에서 정원 초과 0건 / 중복 결제 0건 / 테스트 카드로 결제 성공 |
| **5. 취소·환불·후기** | 1.5주 | 환불 정책 계산, PG 취소, 호스트 취소, 출석 체크, 후기·신고 | 환불액 계산 자동 테스트 통과, 테스트 결제 실제 취소 확인 |
| **6. 호스트 운영** | 1주 | 대시보드, 참가자 관리, 공지, 매출·정산 내역, 계좌 등록 | 호스트 화면 숫자 = 원장 합계 일치 |
| **7. 관리자** | 1.5주 | 대시보드, 회원/호스트/모임/거래 관리, 수수료 설정, 정산서, 신고, 감사 기록 | 정산서 금액 = 원장 합계, 모든 관리자 행동 기록됨 |
| **8. 출시 준비** | 1주 | 약관·방침 페이지, 보안 점검, 성능 점검, 운영 매뉴얼, 실결제 전환(계약 완료 시) | 체크리스트 전 항목 통과, 소액 실결제·환불 1회 검증 |

**합계: 약 11~12주** (PG 계약·법률 확인은 병행해야 8단계가 지연되지 않습니다)

### 테스트 계획

| 종류 | 대상 | 설명 |
|---|---|---|
| 계산 테스트 | 수수료·쿠폰·환불액·정산 | 수십 가지 금액 경우의 수를 자동 검증 |
| 권한 테스트 | RLS | "참가자 A가 B의 예약을 볼 수 없다" 같은 규칙을 역할별로 자동 검증 |
| 동시성 테스트 | 예약 | 정원 1자리에 동시 요청 20건 → 1건만 성공하는지 |
| 화면 흐름 테스트 | 가입→예약→결제→취소 | 실제 브라우저를 자동으로 조작해 검증 (Playwright) |

### 작업 방식 약속

- 각 단계 시작 시 "이번에 만들 것 / 만들지 않을 것"을 먼저 말씀드립니다.
- 끝나면 "실제 동작 확인한 것 / 아직 안 된 것 / 테스트 결과"를 숨김없이 보고합니다.
- 테스트 결제는 항상 "테스트"라고 표시하며, 실결제 구현 완료로 표현하지 않습니다.

|---|---|---|
| 1 | 서비스(브랜드) 이름과 도메인 | 미정이면 임시 이름으로 개발 후 교체 가능 |
| 2 | PG사 | **토스페이먼츠** 단독 or **포트원**(여러 PG를 한 번에 연결하는 중개 서비스). 초기엔 토스페이먼츠 직접 연동이 단순. 정산대행 상품 여부를 함께 문의 |
| 3 | 로그인 방식 | 이메일 + 카카오 (네이버·애플은 후속) |
| 4 | 수수료 계산 기준 | **정가 기준**, 단 호스트 부담 쿠폰은 할인 후 금액 기준 (3장 예시) |
| 5 | PG 결제 수수료 부담 | **플랫폼 부담**(호스트에게 "수수료 30%에 결제수수료 포함"으로 단순 안내) |
| 6 | 기본 환불 정책 | 7일 전 100% / 3일 전 50% / 이후 0%, 호스트 취소 100% (법률 검토 필요) |
| 7 | 정산 주기 | 모임 종료 후 **7일 지나고**, 월 2회(15일·말일) 정산 |
| 8 | 호스트에게 참가자 전화번호 공개 여부 | **비공개**(플랫폼 공지로 연락) + 당일 긴급용 연락만 제한 공개 |
| 9 | 휴대폰 본인인증 | MVP는 휴대폰 번호 입력만, 본인인증(PASS 등)은 유료라 후속 |
| 10 | 쿠폰 화면을 MVP에 포함할지 | 2단계 (구조는 MVP에 포함) |
| 11 | 1회 예약 인원 | 1인 (동반 예약은 후속) |
| 12 | 호스트 승인 기준 | 관리자 수동 심사 (기준표는 함께 작성) |

## 부록 A. 용어 사전

| 용어 | 쉬운 설명 |
|---|---|
| 프론트엔드 / 백엔드 | 사용자가 보는 화면 / 화면 뒤에서 데이터를 처리하는 서버 |
| DB (데이터베이스) | 모든 정보를 표 형태로 저장하는 장부 |
| 테이블 / 컬럼 / 행 | 장부의 표 / 표의 세로 칸(항목) / 표의 가로 줄(한 건) |
| RLS (Row Level Security) | 표의 한 줄 한 줄마다 "누가 볼 수 있나"를 DB가 직접 검사하는 기능 |
| API | 화면이 서버에 "이거 해줘"라고 요청하는 창구 |
| PG (Payment Gateway) | 카드 결제를 대신 처리해주는 결제대행사 |
| 웹훅 (Webhook) | 다른 서비스(PG사)가 우리 서버로 결과를 자동으로 알려주는 알림 |
| 멱등성 키 (Idempotency key) | 같은 요청이 여러 번 와도 한 번만 처리되게 하는 고유 번호 |
| 원장 (Ledger) | 돈의 움직임을 고치지 않고 계속 추가만 하는 장부 |
| 대사 (Reconciliation) | 우리 장부와 PG사 장부를 비교해서 틀린 곳을 찾는 작업 |
| 스냅샷 | 특정 시점의 값을 복사해 고정해 두는 것 |
| 마이그레이션 | DB 표 구조를 바꾼 이력을 파일로 남겨 순서대로 적용하는 방식 |
| 환경변수 | 비밀번호·키를 코드 밖 안전한 설정에 보관하는 방법 |
| 스테이징 | 실제 서비스 직전에 점검하는 복제 환경 |
| MVP | 핵심 가치를 검증할 수 있는 최소 기능 제품 |
| 서비스 키 | 모든 권한을 무시하는 마스터키. 서버에서만 사용 |
