## 1. 사업 분석과 개발 요구사항

### 1-1. 시스템 관점의 사업 구조

이 플랫폼은 **양면 마켓플레이스**(쉬운 설명: 파는 사람과 사는 사람을 연결하고 수수료를 받는 장터)입니다. 시스템이 반드시 잘해야 하는 것은 세 가지입니다.

1. **신뢰** — 결제·환불·정산 금액이 정확히 기록되고 틀리지 않는다.
2. **공급(호스트) 확보** — 호스트가 쉽게 모임을 만들고 운영하고 정산받는다.
3. **수요(참가자) 전환** — 모임을 보고 3번 이내의 터치로 예약까지 간다.

차별점 4가지(호스트 육성·호스트 네트워크·참가자 연결·콘텐츠 지원)는 이 세 가지가 먼저 작동해야 효과가 납니다. 따라서 **MVP에서는 데이터 구조만 준비하고 기능은 이후 단계에서 개발**합니다.

### 1-2. 기능 요구사항

**참가자** — 가입/로그인(이메일·카카오), 프로필·관심사, 모임 탐색(카테고리·날짜·지역·가격·검색), 상세, 예약(1~호스트 허용 인원)·결제, 예약 내역, 취소·환불 신청(규정에 따라 환불액 자동 계산·사전 표시), 출석 후 후기, 호스트 팔로우, 모임 저장

**호스트** — 호스트 신청→승인, 프로필, 모임 개설(임시저장→검수→공개)·수정, 회차 관리, **1인당 최대 예약 인원 설정(1~4)**, 활성화된 환불 규정 중 선택, 참가자 목록(연락처 제외), 출석 체크, 공지·안내 작성, 매출·수수료·정산 예정액·정산 내역 확인, 정산 계좌 등록

**관리자** — 회원·호스트·모임 관리(승인/반려/정지), 결제·환불 조회·처리, 수수료 등급 설정, **환불 규정 관리**, 쿠폰 관리, **수동 정산(정산서 생성→검토→확정→지급 기록)**, 후기·신고 처리, 통계, 감사 기록 조회

### 1-3. 비기능 요구사항

| 구분 | 기준 |
|---|---|
| 보안 | 모든 데이터 접근은 DB 단에서 권한 재검증(RLS). 비밀키는 환경변수에만 |
| 정합성 | 정원 초과 0건, 중복 결제 0건. 금액은 서버가 계산 |
| 추적성 | 돈의 움직임은 수정·삭제 없이 **추가만**(원장 방식). 관리자 행동 전부 기록 |
| 개인정보 | 최소 수집, 호스트에게 연락처 비공개, 국내 리전(서울) 서버 우선 |
| 운영 | 테스트/운영 환경 완전 분리(DB·결제키·데이터) |
| 성능 | 모바일 4G 기준 첫 화면 2.5초 이내 목표 |
| 변경 용이성 | 브랜드명·수수료율·환불 규정·기능 켜기/끄기를 코드 수정 없이 변경 |

### 1-4. 개발 전에 확인해야 할 사업적 포인트

법률·PG·세무 항목은 **9장 "출시 전 별도 검토 항목"**으로 분리해 체크리스트로 정리했습니다. 개발은 이 확인과 **병행**하되, 확인 결과에 따라 달라질 수 있는 부분(자동 정산, 주류 모임 노출, 환불 규정 활성화 등)은 **잠금 상태로 설계**해 확인 전에는 작동하지 않게 합니다.

## 2. 시스템 아키텍처

### 2-1. 전체 그림

```
 [참가자/호스트/관리자의 휴대폰·PC 브라우저]
                 │  (HTTPS 암호화 통신)
                 ▼
 ┌─────────────────────────────────────────────┐
 │  Vercel (웹사이트를 띄워주는 서버, 서울 리전 우선)  │
 │  Next.js 앱                                   │
 │   ├─ 화면(페이지)                               │
 │   ├─ 서버 처리: 예약·결제 승인·환불·정산           │
 │   └─ 결제 웹훅 수신 창구 ← 토스페이먼츠가 결과 통보   │
 └───────┬───────────────────────┬─────────────┘
         │                       │ (서버끼리 비밀키로 통신)
         ▼                       ▼
 ┌──────────────────┐     ┌──────────────────────┐
 │ Supabase(서울 리전) │     │ 토스페이먼츠          │
 │  ├ PostgreSQL DB  │     │  테스트 키 / 실제 키 분리 │
 │  │  + RLS(권한규칙) │     │  ※ 지급대행 API는 미연동  │
 │  ├ Auth (로그인)   │     └──────────────────────┘
 │  ├ Storage (사진)  │     ┌──────────────────────┐
 │  └ 예약 만료 등 정기작업│     │ 이메일 발송 (Resend 등) │
 └──────────────────┘     └──────────────────────┘
```

### 2-2. 구성요소 역할

| 구성요소 | 비유 | 하는 일 |
|---|---|---|
| **Next.js** | 매장 인테리어 + 카운터 | 화면 표시, 중요한 처리는 서버 쪽 코드에서 실행 |
| **Supabase PostgreSQL** | 금고 겸 장부 | 모든 데이터 저장 |
| **RLS** (행 단위 보안) | 장부 줄마다 붙은 자물쇠 | "본인만 / 이 모임 호스트만 / 관리자만"을 DB가 직접 검사 |
| **Supabase Auth** | 출입증 발급처 | 가입·로그인·카카오 로그인 |
| **Supabase Storage** | 사진 창고 | 모임·프로필 사진. 창고에도 권한 규칙 |
| **토스페이먼츠** | 카드 단말기 회사 | 결제 승인과 취소 |
| **웹훅** | PG사가 거는 확인 전화 | 결제/취소 결과를 PG사가 서버로 직접 통보 |

### 2-3. 환경 분리

| 환경 | 용도 | DB | 결제 |
|---|---|---|---|
| 로컬 | 개발 | 로컬 Supabase | 토스 테스트 키 |
| 스테이징 | 창업자 검수용 | 별도 Supabase 프로젝트 | 토스 테스트 키 |
| 운영 | 실제 서비스 | 별도 Supabase 프로젝트 | 토스 실제 키 (계약 후) |

- 비밀키는 Vercel/Supabase 환경변수에만 저장. `.env.example`에는 이름만 적습니다.
- 결제 기록마다 `test/live` 표시를 남겨 테스트 결제가 운영 장부에 섞이지 않게 합니다.

### 2-4. 코드 구조 예정안

```
app/
  (public)/        홈, 모임 목록, 상세, 호스트 프로필, 약관·고지 페이지
  (participant)/   마이페이지, 예약 내역, 결제, 후기
  host/            호스트 화면
  admin/           관리자 화면
  api/payments/    결제 승인, 웹훅
config/
  brand.ts         ★ 브랜드명·로고·연락처 등 (2-5)
lib/
  domain/          금액 계산(수수료·쿠폰·환불·정산) — 자동 테스트 필수
  payments/        결제사 연결부 (토스 구현체 1개, 교체 가능 구조)
  supabase/        DB 연결
supabase/
  migrations/      DB 구조 변경 이력
  tests/           권한(RLS) 테스트
tests/             계산·흐름 자동 테스트
```

### 2-5. 브랜드명 변경 용이성 (검토 의견 8)

| 원칙 | 방법 |
|---|---|
| 이름을 코드에 직접 쓰지 않는다 | 모든 화면·메일·약관은 `config/brand.ts`의 값(서비스명, 법인명, 고객센터, 로고 경로, 대표 색상)을 불러서 표시 |
| 환경별로 바꿀 수 있다 | 서비스 주소(도메인)·발신 이메일은 환경변수 |
| DB에 브랜드명을 저장하지 않는다 | 데이터는 브랜드와 무관하게 유지 → 이름 변경 시 데이터 이전 불필요 |
| 디자인 색·글꼴은 한 곳에서 관리 | 디자인 토큰(색·글꼴 변수)으로 관리 → 브랜드 확정 시 일괄 교체 |
| 법적 문서도 변수 처리 | 약관·개인정보처리방침의 회사명·대표자·사업자번호 등은 설정값 사용 |

> 브랜드 확정 시 작업: 설정 파일 1개 + 로고 이미지 + 도메인 연결 정도로 끝나도록 합니다.

### 2-6. 결제·정산 구조 (검토 의견 1)

**결제**
- 토스페이먼츠 결제위젯/결제창 방식 + 서버 승인 방식으로 설계합니다.
- 결제사 연결부는 한 폴더(`lib/payments`)로 격리해, 계약 결과에 따라 다른 PG나 계약 유형(예: 오픈마켓형 하위몰 구조)으로 바뀌어도 다른 코드는 영향이 적게 합니다.

**정산 — 단계적 잠금**
```
[현재 설계 범위]  수동 정산 모드만 존재
   시스템: 금액 계산·기록·정산서 생성
   사람(관리자): 금액 확인 → 은행에서 직접 이체 → 시스템에 '지급 완료' 기록

[잠금 상태]  자동 정산 / 지급대행 API 연동
   조건: ① 토스페이먼츠 계약 유형 확정 ② 정산대행(지급대행) 가능 여부 확인
         ③ 전자금융거래법 등 법률 검토 완료 → 창업자 승인
   → 위 조건 충족 전까지 코드 자체를 작성하지 않음
```
- 운영 설정에 `정산 방식 = 수동(manual)`만 존재하며, 자동 방식 값은 정의하지 않습니다.
- 수동 정산이라도 DB 구조(정산서·지급 기록)는 나중에 자동 정산으로 바꿀 때 그대로 쓸 수 있게 합니다.

## 3. 데이터베이스 설계

### 3-1. 핵심 개념

- **모임(meetup)**: 제목·설명·사진·가격·규정 등 "상품 정보"
- **회차(session)**: 날짜·장소·정원·예약 인원 등 "한 번의 실제 진행"
- **예약(booking)**: 한 회차에 대한 한 사람의 주문. **인원(1~4명)** 포함
- **원장(ledger)**: 돈이 움직일 때마다 추가되는 기록장

MVP 화면은 "모임 1개 = 회차 1개"처럼 보여도 DB는 분리해 반복 모임 확장에 대비합니다.

### 3-2. 테이블 관계도

```
users(로그인 계정, Supabase 관리)
  └─1:1─ profiles(회원)  ─1:1─ profile_private(전화번호 등 비공개 정보)
            ├─1:N─ user_roles(권한)
            ├─1:1─ host_profiles(호스트, 등급, 승인상태)
            │         ├─1:N─ meetups(모임) ──── refund_policy_versions(환불 규정 버전)
            │         │        ├─1:N─ meetup_images
            │         │        ├─1:N─ meetup_sessions(회차)
            │         │        │        ├─1:N─ bookings(예약, 인원 1~4)
            │         │        │        │        ├─1:N─ payments ─1:N─ refunds
            │         │        │        │        ├─1:N─ ledger_entries(원장)
            │         │        │        │        ├─0:1─ coupon_redemptions
            │         │        │        │        ├─0:1─ reviews
            │         │        │        │        └─0:1─ settlement_items
            │         │        │        └─1:N─ announcements(공지·안내)
            │         │        └─N:M─ meetup_hosts(공동 호스트) [확장용]
            │         ├─1:N─ payout_accounts(정산 계좌)
            │         └─1:N─ settlements(정산서) ─1:N─ settlement_items, payout_records
            ├─N:M─ follows / saved_meetups
            └─1:N─ reports / notifications

설정류: commission_tiers, refund_policies, refund_policy_versions, meetup_types,
        categories, coupons, platform_settings
기록류: audit_logs, payment_webhook_events, legal_consents
확장용: collaboration_proposals, user_activity_events, host_resources, host_growth_records
```

### 3-3. 테이블별 상세

> **PK**=고유번호, **FK**=다른 표를 가리키는 연결고리. 금액은 모두 **원 단위 정수**, 비율은 **만분율 정수**(30% → 3000)로 저장해 소수점 오차를 없앱니다.

#### (1) 회원·권한

**profiles** — 공개 가능한 회원 정보: id, nickname, avatar_url, bio, interests, status(active/suspended/withdrawn)

**profile_private** — 비공개 정보 (★ 검토 의견 6)
| 컬럼 | 설명 |
|---|---|
| user_id | |
| phone | 전화번호 — **본인과 관리자만** 접근. 호스트는 어떤 경로로도 조회 불가 |
| birth_year | 연령 제한 모임 참가 확인용 |
| adult_verified_at | 성인 확인 시각(주류 모임용, 방식은 9장 검토 후 확정) |
| marketing_agreed_at | 마케팅 수신 동의 |

> 전화번호를 별도 표로 분리하는 이유: 프로필 표는 다른 사람(호스트 등)에게 일부 공개되므로, 같은 표에 두면 실수로 노출될 위험이 있습니다. 표 자체를 분리해 호스트에게는 접근 권한을 아예 주지 않습니다.

**user_roles** — participant / host / admin. 회원 스스로 수정 불가, 관리자만 부여(기록 남음)

**host_profiles** — display_name, intro, expertise, sns_links, cover_image, status(applied/approved/rejected/suspended), tier_id, custom_commission_rate(예외 수수료, 선택), business_type(개인/개인사업자/법인), approved_by/at

**commission_tiers** — 관리자 화면에서 수정 (초기값 = 가설)
| code | 이름 | 초기 수수료율 |
|---|---|---|
| new | 신규 호스트 | 30% |
| growing | 성장 호스트 | 25% |
| excellent | 우수 호스트 | 20% |
| partner | 핵심 파트너 | 15% |

> 결제 시점의 수수료율을 예약에 복사(스냅샷)합니다. 등급표를 바꿔도 과거 거래는 변하지 않습니다.

#### (2) 모임

**meetup_types** — 모임 유형 (관리자 관리, 환불 규정·운영 요건 연결용)
| 컬럼 | 설명 |
|---|---|
| code, name | 예: `general`(일반 모임), `class`(재료가 드는 클래스·워크숍), `alcohol`(주류 포함), `outdoor`(야외·여행) |
| requires_adult | 성인만 참가 가능 여부 (주류 등) |
| requires_legal_review | 법률 검토 완료 전 공개 불가 여부 |
| is_enabled | 운영 가능 여부 (예: 주류 유형은 9장 검토 완료 전 `false`) |

**meetups**
| 컬럼 | 설명 |
|---|---|
| id, host_id, category_id, meetup_type_id | |
| title, summary, description, tags | |
| cover_image_url | 추가 사진은 meetup_images |
| unit_price | 1인 참가비(원) |
| **max_quantity_per_booking** | ★ 1인당 최대 예약 인원. 기본 1, **1~4만 허용**(DB 규칙으로 강제) |
| target_audience, requirements, min_age | 참가 대상·조건 |
| agenda | 진행 시간표(구조화 목록) |
| what_to_bring | 준비물 |
| refund_policy_id | 관리자가 활성화한 환불 규정 중 선택 |
| status | draft → pending_review → published / rejected / archived / suspended |
| avg_rating, review_count | 자동 계산 |

**meetup_sessions** — starts_at, ends_at, venue_name, address(공개), address_detail(**확정 참가자에게만** 공개), capacity(정원, 명), reserved_count(예약된 **인원 합계**, DB만 수정), booking_deadline, status(open/full/closed/completed/cancelled)

**announcements** — 공지·안내 (★ 검토 의견 6)
| 컬럼 | 설명 |
|---|---|
| session_id, author_id | 해당 회차 확정 참가자 전체 대상 |
| type | notice(일반 공지) / guide(장소·준비 안내) / change(일정·장소 변경) / cancel(취소 안내) |
| title, body | |
| is_pinned | 상단 고정 |
| send_email | 이메일로도 발송 여부 |

> 회차 시작 전날 리마인더(장소·시간·준비물)는 시스템이 자동 발송.

#### (3) 예약 — 인원 1~4명 (검토 의견 3)

**bookings**
| 컬럼 | 설명 |
|---|---|
| id, session_id, user_id | |
| **quantity** | 예약 인원. `1 ≤ quantity ≤ 모임의 max_quantity_per_booking` (DB 함수가 검증) |
| status | 아래 상태 흐름 |
| hold_expires_at | 결제 대기 좌석 확보 만료(10분) |
| refund_policy_version_id | ★ 예약 시점의 환불 규정 버전 고정 |
| commission_rate_snapshot | 결제 시점 수수료율 |
| (금액 필드) | 아래 3-6 "금액 기록 구조" 참고 |
| attended_count | 출석 인원 (0~quantity) |
| cancelled_by, cancel_reason, cancelled_at | |

- **동반 인원 개인정보는 받지 않습니다.** 예약자 1명이 대표로 책임지며 인원수만 기록합니다.
- **MVP 취소는 예약 전체 취소만** 지원합니다(3명 중 1명만 취소하는 "부분 취소"는 후속). 단, 환불 표에는 인원 정보를 둬서 나중에 부분 취소를 붙일 수 있게 합니다.
- 후기는 예약 1건당 1개(예약자 작성).

**예약 상태 흐름**
```
pending_payment(결제 대기, 인원만큼 좌석 10분 확보)
   ├─ 결제 성공(서버가 토스에 직접 확인) → confirmed
   └─ 10분 초과 / 결제 실패 → expired (좌석 반환)
confirmed
   ├─ 참가자 취소 → cancelled_by_user → 환불 규정 계산 → refunded / partially_refunded / no_refund
   ├─ 호스트·관리자 취소 → cancelled_by_host → 전액 환불
   └─ 모임 종료 → completed (출석 인원 기록)
```

#### (4) 결제·환불·원장·정산 (검토 의견 1, 2)

**payments** — order_id(고유), idempotency_key(고유), pg_provider(`tosspayments`), pg_payment_key(고유), method, amount, pg_fee, pg_fee_source(추정/PG정산자료 확정), status, environment(test/live), raw_response(민감정보 제외)

**refunds** — payment_id, booking_id, refund_quantity, refund_rate_applied, calculated_amount(규정에 따른 자동 계산액), approved_amount, override_reason(관리자 예외 조정 시 필수), status(requested/approved/processing/completed/rejected/failed), pg_cancel_key

**ledger_entries** — 거래 원장 (수정·삭제 불가, 추가만)
| entry_type | 의미 |
|---|---|
| gross_sale | 할인 전 금액 |
| coupon_platform | 플랫폼 부담 쿠폰 할인 |
| coupon_host | 호스트 부담 쿠폰 할인 |
| pg_fee | 결제 수수료 |
| platform_commission | 플랫폼 수수료 |
| host_payable | 호스트 정산 예정액 |
| refund_* | 환불 시 위 항목들의 반대 기록 |
| tax_withholding | 원천징수(해당 시, 9장 세무 검토 후 활성화) |
| adjustment | 관리자 수기 조정(사유·승인자 필수) |

**payout_accounts** — 은행, 계좌번호(**암호화 저장**, 화면엔 뒤 4자리만), 예금주, 확인 상태(미확인/관리자 확인 완료)

**정산 상태 관리 (수동 정산)** — 예약 단위와 정산서 단위 두 층으로 관리합니다.

예약별 정산 상태 (`bookings.settlement_status`)
| 상태 | 의미 |
|---|---|
| not_eligible | 아직 정산 대상 아님 (모임 전, 환불 진행 중 등) |
| eligible | 정산 가능 (모임 종료 + 환불 가능 기간 경과 + 분쟁 없음) |
| in_statement | 정산서에 포함됨 |
| paid | 지급 완료 |
| on_hold | 보류 (신고·분쟁·호스트 노쇼 등, 사유 필수) |
| excluded | 정산 제외 (전액 환불 등) |

정산서 (`settlements`)
| 컬럼 | 설명 |
|---|---|
| host_id, period_start, period_end | 정산 기간 |
| gross_amount | 할인 전 금액 합계 |
| paid_amount | 참가자 실제 결제액 합계 |
| coupon_platform_amount / coupon_host_amount | 부담 주체별 쿠폰 합계 |
| commission_amount | 플랫폼 수수료 합계 |
| pg_fee_amount | PG 수수료 합계 (플랫폼 부담분 기록용) |
| refund_amount | 환불 합계 |
| adjustment_amount | 조정 합계 |
| tax_amount | 원천징수(해당 시) |
| payout_amount | **최종 호스트 지급액** |
| status | draft(생성) → reviewed(1차 검토) → confirmed(확정, 금액 잠금) → paid(지급 완료) / on_hold / cancelled |
| created_by, reviewed_by, confirmed_by | 단계별 처리자 (같은 사람이 생성·확정 못하도록 옵션) |

**settlement_items** — 정산서에 포함된 예약 목록. 한 예약은 한 정산서에만 들어가도록 고유 규칙.

**payout_records** — 실제 지급 기록 (수동)
| 컬럼 | 설명 |
|---|---|
| settlement_id, amount, paid_at | |
| method | `manual_bank_transfer` (현재 유일한 값) |
| bank_reference | 이체 확인번호/메모 |
| evidence_file | 이체 확인증 첨부(관리자만 열람) |
| recorded_by | 기록한 관리자 |

> 정산서 금액은 항상 원장에서 자동 합산하며, 관리자가 숫자를 직접 고칠 수 없습니다. 조정이 필요하면 사유와 함께 `adjustment` 원장 기록을 추가합니다.

| 향후 기능 | 미리 준비하는 구조 | 지금 준비하는 이유 |
|---|---|---|
| **호스트 협업** | `meetup_hosts`(모임별 공동 호스트, 역할, 수익 배분 비율), `collaboration_proposals`(제안·수락 상태) | MVP에서도 모든 모임에 "주 호스트 1명"을 이 표에 기록 → 나중에 공동 호스트가 붙어도 정산 구조 변경 불필요. 원장·정산 항목은 처음부터 `host_id` 단위로 기록 |

| **콘텐츠 지원** | `meetup_images.source`(호스트 업로드/플랫폼 제작 구분) | 추후 촬영 지원 시 저작권 귀속 구분 |

> v0.1에서 MVP에 넣었던 "기획 템플릿 3~5종, 운영 가이드 페이지"는 검토 의견에 따라 **MVP에서 제외**합니다.

### 3-4. 중복 예약·초과 예약·중복 결제 방지

| 위험 | 방지 방법 |
|---|---|
| 같은 사람이 같은 회차에 예약을 여러 개 | "한 사람은 한 회차에 유효 예약 1건만" DB 고유 규칙. 인원을 늘리려면 취소 후 재예약 (MVP) |
| 허용 인원 초과 (예: 최대 2명인데 4명) | DB 함수가 `quantity ≤ max_quantity_per_booking` 검증 + DB 제약으로 1~4 범위 강제 |
| 남은 자리 2개에 3명 예약 / 동시 예약 | 좌석 확보를 DB 함수 하나에서 처리하며 해당 회차를 **잠금** → `예약 인원 합계 + 신청 인원 ≤ 정원`일 때만 확보. 부족하면 "남은 자리 n명" 안내 |
| 결제 버튼 연타·재시도 | 결제 요청마다 고유 열쇠(멱등성 키), PG 거래번호 고유 규칙 |
| 결제는 됐는데 서버 처리 실패 | 토스 웹훅 + 주기적 대사(우리 기록 vs PG 기록 비교)로 자동 복구, 불일치 시 관리자 경고 |
| 금액 조작 | 금액은 서버가 `단가 × 인원 − 쿠폰`으로 계산, 토스 승인 금액과 불일치 시 자동 취소 |
| 결제 성공 위조 | 서버가 토스에 직접 확인한 경우에만 확정 |
| 결제 대기 좌석 묶임 | 10분 후 자동 만료·반환 |

### 3-5. 환불 규정 — 관리자 설정형 (검토 의견 4)

**원칙**
1. 환불 비율·기한은 **코드에 고정하지 않고** 관리자가 DB 설정으로 관리합니다.
2. 규정은 **버전**으로 관리합니다. 수정하면 새 버전이 생기고, **기존 예약은 예약 당시 버전**으로 계산합니다.
3. **법률 검토 완료로 표시된 규정만 활성화**할 수 있습니다. 활성화 전에는 호스트가 선택할 수 없습니다.
4. 모임 유형별로 사용할 수 있는 규정을 제한할 수 있습니다(예: 재료 준비가 필요한 클래스형 전용 규정).
5. 호스트·플랫폼 사유 취소는 규정과 무관하게 **전액 환불**(시스템 고정 규칙, 법적 최소 보호선).

**refund_policies / refund_policy_versions**
| 컬럼 | 설명 |
|---|---|
| name, description | 예: "일반형", "클래스형" (이름·내용은 법률 검토 후 결정) |
| allowed_meetup_types | 적용 가능한 모임 유형 |
| rules | 구간별 환불 비율 목록 — 예: [{"기준": "시작 N일 전까지", "환불율": X%}, …] |
| cutoff_basis | 기준 시각(회차 시작 시각, 한국시간) |
| cooling_off_rule | 결제 후 일정 시간 내 무조건 전액 환불 등 청약철회 관련 규칙(검토 결과 반영용) |
| host_cancel_rate | 호스트 취소 시 100% (변경 불가) |
| force_majeure_rule | 천재지변·감염병 등 불가항력 시 처리 |
| rounding_rule | 원 단위 처리 방식 |
| review_status | draft → legal_reviewed → active → retired |
| legal_reviewed_by, legal_reviewed_at, legal_memo | 누가 언제 어떤 근거로 검토했는지 |
| display_text | 참가자에게 보여줄 안내 문구 (상세·결제·취소 화면에 동일 표시) |

**검토가 필요한 법규 (9장 상세)** — 전자상거래법상 청약철회 규정과 그 예외, 공정거래위원회 소비자분쟁해결기준 중 해당 업종 기준 존재 여부, 약관규제법상 과도한 위약금 조항 무효 가능성, 표시·고지 의무.

> v0.1의 "7일 전 100% / 3일 전 50% / 이후 0%"는 **확정 정책이 아니며 예시로만** 남습니다. 실제 규정은 9장 검토 후 관리자가 등록합니다. 개발 중에는 "테스트용 규정"으로만 동작을 검증합니다.

**관리자 예외 처리**: 분쟁·특수 상황 시 계산액과 다른 금액으로 환불 가능 — 사유 필수, 감사 기록, 원장에 별도 기록.

### 3-6. 금액 기록 구조 — 쿠폰·수수료·정산 (검토 의견 2, 5)

예약 1건마다 다음 금액을 **모두 따로 저장**합니다.

| 필드 | 의미 | 계산 |
|---|---|---|
| unit_price | 1인 참가비 | 모임 가격 스냅샷 |
| quantity | 인원 | 1~4 |
| **list_amount** | 할인 전 금액 | unit_price × quantity |
| discount_platform | 플랫폼 부담 할인 | 쿠폰 규칙 |
| discount_host | 호스트 부담 할인 | 쿠폰 규칙 |
| **paid_amount** | 실제 결제 금액 | list_amount − 할인 합계 |
| **commission_base** | 수수료 산정 기준액 | list_amount − discount_host (제안안, 10장 확정 필요) |
| commission_rate | 적용 수수료율 | 결제 시점 스냅샷 |
| **commission_amount** | 플랫폼 수수료 | commission_base × rate |
| **host_payout_amount** | 호스트 정산 예정액 | commission_base − commission_amount |
| pg_fee | PG 수수료 | 토스 계약 요율 / 정산자료로 확정 |
| platform_net | 플랫폼 순수익 | commission_amount − discount_platform − pg_fee |

**계산 예시 1 — 2명 예약 + 플랫폼 부담 쿠폰** (PG 수수료 3.3%는 가정값)
```
1인 30,000원 × 2명 = 할인 전 60,000원 / 수수료 30% / 플랫폼 부담 쿠폰 6,000원
실제 결제액        = 60,000 − 6,000     = 54,000원
수수료 기준액      = 60,000 − 0         = 60,000원   (플랫폼 쿠폰은 호스트에 영향 없음)
플랫폼 수수료      = 60,000 × 30%       = 18,000원
호스트 정산 예정액 = 60,000 − 18,000    = 42,000원
PG 수수료          = 54,000 × 3.3%      =  1,782원
플랫폼 순수익      = 18,000 − 6,000 − 1,782 = 10,218원
```
**계산 예시 2 — 같은 조건, 호스트 부담 쿠폰**
```
실제 결제액 54,000 / 수수료 기준액 54,000 / 수수료 16,200 / 호스트 정산 37,800
PG 수수료 1,782 / 플랫폼 순수익 14,418
```
**환불 시**: 환불율을 적용해 위 항목을 비례 차감하는 반대 원장 기록을 추가합니다(예: 50% 환불이면 수수료·정산 예정액도 50% 차감). 원 단위 끝수 처리 규칙과 PG 수수료 환급 여부는 토스 계약 조건 확인 후 확정합니다.

> 이 계산은 `lib/domain`의 한 곳에서만 수행하고, 경우의 수(인원 1~4 × 쿠폰 유형 × 환불율 × 끝수)를 자동 테스트로 검증합니다.

## 4. 권한 구조

### 4-1. 3중 방어

```
1단계 화면: 권한 없는 버튼 숨김            ← 편의용, 보안 아님
2단계 서버: 모든 요청에서 로그인·권한 확인
3단계 DB:   RLS로 데이터 한 줄씩 접근 검사   ← 최종 방어선, 자동 테스트로 검증
```

### 4-3. 구현 원칙

- 권한 판단은 `user_roles` 표 기준. 회원이 수정할 수 있는 값은 권한 판단에 사용 금지.
- 돈·좌석·상태 변경(예약, 결제 확정, 환불, 정산)은 **DB 함수로만** 가능. 일반 사용자에게 해당 표 직접 수정 권한 없음.
- 모든 권한을 무시하는 **서비스 키**는 웹훅 등 서버 코드에서만 사용, 브라우저로 전달 금지.
- 관리자 2단계 인증(OTP) 필수. 관리자의 개인정보 열람·금액 조정은 감사 기록.
- Storage(사진 창고)도 경로별 권한, 이체 확인증 등 민감 파일은 관리자 전용.

**관리자** (`/admin/...`) — 대시보드(오늘 할 일) / 회원 / 호스트 승인 / 모임 검수 / 모임 유형 / 거래(결제·환불) / **환불 규정 관리(버전·검토 상태)** / 수수료 등급 / 쿠폰 / **정산(예약별 정산 상태 → 정산서 → 확정 → 지급 기록)** / 신고·후기 / 감사 기록 / 운영 설정

### 5-2. 핵심 흐름

**A. 참가자 예약**
```
상세 → 회차 선택 → 인원 선택(1~허용 인원, 남은 자리 이내) → [예약하기]
 → (비로그인 시 로그인 후 복귀)
 → 결제 페이지: 서버가 인원만큼 좌석 10분 확보 + 금액 계산 + 환불 규정 버전 고정
 → 토스 결제 → 서버가 토스에 직접 확인 → 확정 + 원장 기록 + 확정 안내
 → 전날 자동 리마인더 / 호스트 공지는 '예약 내역'과 이메일로 수신
 → 당일 호스트 출석 체크 → 종료 후 후기 요청
```

**B. 취소·환불**
```
예약 내역 → [취소] → 예약 시점 규정 버전으로 예상 환불액 표시 → 확인
 → 서버 재계산 → 토스 취소 → 성공 시 환불 완료 + 반대 원장 기록 + 좌석 반환 + 쿠폰 복구(규칙에 따라)
 → 토스 오류 시 '환불 처리중' + 관리자 경고
```

**C. 호스트 ↔ 참가자 소통 (전화번호 없이)**
```
호스트: 공지 작성(유형: 일반/안내/변경/취소) → 해당 회차 확정자 전원에게
        사이트 알림 + 이메일 발송
참가자: 예약 내역에서 공지 확인
긴급 상황: 참가자·호스트 모두 '운영팀 문의'로 플랫폼에 연락 → 관리자가 중재
(참가자↔호스트 1:1 메시지는 MVP 제외, 후속 검토)
```

**D. 수동 정산 (관리자)**
```
① 정산 기간 마감 → 시스템이 eligible 예약을 호스트별로 묶어 정산서 draft 생성
② 관리자 검토(reviewed): 거래별 결제액·수수료·쿠폰·환불·PG 수수료 확인, 문제 건 on_hold
③ 확정(confirmed): 금액 잠금, 호스트 화면에 '지급 예정' 표시
④ 관리자가 은행에서 직접 이체
⑤ 지급 기록(paid): 이체 확인번호·확인증 첨부 → 호스트 화면 '지급 완료'
※ 모든 단계 감사 기록. 자동 이체 없음.
```

## 8. 개발 순서와 작업 계획

> 각 단계 종료 시 스테이징 주소로 직접 확인 → 승인 후 다음 단계.

| 단계 | 기간 | 만드는 것 | 완료 기준 |
|---|---|---|---|
| **0. 기반** | 0.5주 | 프로젝트 생성, 브랜드 설정 구조, 디자인 토큰, Supabase(서울)·Vercel 연결, 환경 분리 | 스테이징에 빈 홈 표시, 브랜드명 설정 변경 시 화면 반영 |
| **1. 회원·권한** | 1주 | 가입·로그인, 공개/비공개 프로필 분리, 권한 표, RLS, 관리자 2단계 인증 | 역할별 접근 차이 + RLS 테스트(전화번호 차단 포함) 통과 |
| **2. 호스트·모임** | 1.5주 | 호스트 승인, 모임 유형, 모임 개설·사진·회차·최대 예약 인원, 검수 | 승인 후에만 공개, 인원 설정 1~4 외 값 거부 |
| **3. 탐색** | 1.5주 | 홈, 목록, 카테고리, 상세(인원 선택·남은 자리), 호스트 프로필, 저장·팔로우 | 모바일 탐색 흐름 확인 |
| **4. 금액 엔진·예약·결제** ★ | 2주 | 금액 계산 모듈(쿠폰·수수료·정산 예정액), 좌석 확보, 토스 테스트 결제, 검증, 웹훅, 원장, 만료, 쿠폰 적용 | 동시 예약 테스트 정원 초과 0건 / 중복 결제 0건 / 금액 계산 테스트 전부 통과 |
| **5. 환불 규정·취소·후기** | 1.5주 | 환불 규정 버전·검토 상태, 환불 계산, 토스 취소, 호스트 취소, 출석, 공지·안내·리마인더, 후기·신고 | 규정 버전별 계산 테스트 통과, 테스트 결제 실제 취소 확인 |
| **6. 호스트 운영** | 1주 | 대시보드, 참가자 관리, 매출·정산 내역, 쿠폰 동의, 계좌 | 호스트 화면 숫자 = 원장 합계 |
| **7. 관리자·수동 정산** | 1.5주 | 관리자 화면 전반, 수동 정산 5단계, 감사 기록 | 정산서 = 원장 합계, 확정 후 수정 불가, 모든 행동 기록 |
| **8. 출시 준비** | 1주 | 9장 검토 결과 반영(약관·고지·환불 규정 활성화), 보안·성능 점검, 운영 매뉴얼, 실결제 전환(계약 완료 시) | 체크리스트 통과, 소액 실결제·환불 1회 검증 |

**합계 약 11~12주.** 9장 검토가 늦어지면 8단계(출시)만 지연되고 1~7단계 개발은 진행 가능합니다.

### 테스트 계획

| 종류 | 대상 |
|---|---|
| 금액 계산 | 인원 1~4 × 쿠폰(없음/플랫폼/호스트/분담) × 환불율 × 끝수 처리 |
| 권한(RLS) | 역할별 접근, 호스트의 연락처 접근 차단, 정산서 수정 차단 |
| 동시성 | 남은 자리 2개에 2명·3명 동시 요청 등 |
| 화면 흐름 | 가입→예약(다인원)→결제→공지 수신→취소→환불 (실제 브라우저 자동 조작) |

### 작업 방식 약속

- 단계 시작 시 "만들 것 / 만들지 않을 것"을 먼저 공유합니다.
- 종료 시 "실제 확인한 것 / 안 된 것 / 테스트 결과"를 숨김없이 보고합니다.
- 테스트 결제는 항상 테스트로 표시하며, 실결제·자동 정산 구현 완료로 표현하지 않습니다.

## 9. 출시 전 별도 검토 항목 (법률·PG·세무)

> **확인 주체**: ⚖️ 변호사 / 🧾 세무사 / 💳 토스페이먼츠 / 🏛️ 관할 기관

| D3 | 해외 사업자 서비스 이용 시 국외 이전 고지·동의 필요 여부 (서울 리전 사용 시에도 해당 여부) | ⚖️ | 방침, 동의 화면 |
| D4 | 탈퇴 시 파기 vs. 법정 보존 기간 데이터 분리 보관 방법 | ⚖️ | 탈퇴 처리 로직 |
| D5 | 추천용 활동 기록 수집의 동의 범위 (향후 추천 기능 대비) | ⚖️ | `user_activity_events` 수집 범위 |
| D6 | 호스트 정산 계좌·주민번호(원천징수 시) 등 민감 정보 수집·암호화 기준 | ⚖️ 🧾 | 정산 정보 수집 항목 |
| D7 | 개인정보 보호책임자 지정, 유출 시 신고 절차 | ⚖️ | 운영 매뉴얼 |

## 10. 확정 사항과 남은 결정

### 10-1. 이번 검토로 확정된 사항

| 항목 | 확정 내용 |
|---|---|
| PG | 토스페이먼츠 우선 검토 |
| 정산 | 관리자 수동 확인 방식. 자동 정산은 구현하지 않음 |
| 예약 인원 | 기본 1명, 호스트가 모임별 1~4명 설정 |
| 환불 규정 | 관리자 설정형, 법률 검토 후 활성화. 하드코딩 금지 |
| 쿠폰 | 플랫폼/호스트 부담 구분, 금액 항목별 기록 |
| 전화번호 | 호스트에게 비공개, 공지·안내 기능 제공 |
| 확장 기능 | 협업·추천·육성은 데이터 구조만 |
| 프로젝트명 | Gathering(가칭), 설정 기반 교체 |
| 로그인 | 이메일 + 카카오 (v0.1 제안 유지) |

### 10-2. 승인 시 함께 확정해 주실 사항 (추천안 포함)

| # | 질문 | 추천안 |
|---|---|---|
| 1 | 수수료 산정 기준 | **할인 전 금액 − 호스트 부담 할인** (플랫폼 쿠폰은 호스트 정산에 영향 없음) |
| 2 | PG 수수료 부담 | 플랫폼 부담 (호스트에게는 "수수료에 결제수수료 포함"으로 안내) |
| 3 | 정산 대상 시점 | 모임 종료 후 7일 경과 + 분쟁 없음 → eligible |
| 4 | 정산 주기 | 월 2회(15일·말일 마감) — PG 계약 결과에 따라 조정 |
| 5 | 정산서 생성자와 확정자 분리 | 초기 1인 운영이면 "끔", 운영 인력 2명 이상부터 "켬" |
| 6 | 예약 인원 변경·부분 취소 | MVP 제외 (전체 취소 후 재예약) |
| 7 | 성인 확인 방식 | 주류 유형 잠금 상태이므로 9-5 검토 후 결정 |

| 용어 | 쉬운 설명 |
|---|---|
| 프론트엔드 / 백엔드 | 사용자가 보는 화면 / 화면 뒤에서 데이터를 처리하는 서버 |
| DB / 테이블 / 컬럼 / 행 | 데이터 장부 / 장부의 표 / 표의 항목 칸 / 표의 한 줄(한 건) |
| RLS | 표의 한 줄마다 "누가 볼 수 있나"를 DB가 직접 검사하는 기능 |
| PG | 카드 결제를 대신 처리해주는 결제대행사 (토스페이먼츠 등) |
| 지급대행(정산대행) | PG사가 플랫폼 대신 판매자들에게 대금을 나눠 지급해 주는 서비스 |
| 웹훅 | PG사가 결제 결과를 우리 서버로 자동 통보하는 것 |
| 멱등성 키 | 같은 요청이 여러 번 와도 한 번만 처리되게 하는 고유 번호 |
| 원장 | 돈의 움직임을 고치지 않고 추가만 하는 장부 |
| 대사 | 우리 장부와 PG사 장부를 비교해 틀린 곳을 찾는 작업 |
| 스냅샷 | 특정 시점의 값을 복사해 고정해 두는 것 |
| 버전 관리 | 규정을 고칠 때 덮어쓰지 않고 새 판을 만들어 이전 판도 보존하는 것 |
| 마이그레이션 | DB 구조 변경 이력을 파일로 남겨 순서대로 적용하는 방식 |
| 환경변수 | 비밀번호·키를 코드 밖 안전한 설정에 보관하는 방법 |
| 스테이징 | 실제 서비스 직전에 점검하는 복제 환경 |
| 디자인 토큰 | 색·글꼴 등 디자인 값을 한 곳에 모아 이름 붙여 관리하는 것 |
| 서비스 키 | 모든 권한을 무시하는 마스터키. 서버에서만 사용 |
| MVP | 핵심 가치를 검증할 수 있는 최소 기능 제품 |
