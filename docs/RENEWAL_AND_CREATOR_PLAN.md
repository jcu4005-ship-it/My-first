# GATHERING — 디자인 리뉴얼 & 크리에이터 사업 확장 지시서 (Claude Code 입력용)

> 사용법: 이 파일 전체를 Claude Code에 붙여 넣거나 "docs/RENEWAL_AND_CREATOR_PLAN.md 를 읽고 0단계부터 진행해"라고 지시한다.
> 작성 기준: 2026-11-04 현재 저장소(`claude/community-platform-design-8lg04x` 브랜치)의 실제 상태.
> 이 문서는 **두 개의 트랙**으로 나뉜다. 트랙 A(디자인 리뉴얼)와 트랙 B(크리에이터 사업)는 서로 다른 작업 단위·커밋·승인으로 진행한다.

---

## 0. 반드시 지킬 규칙 (모든 단계 공통)

### 0-1. 진행 방식
1. **0단계(분석·제안)에서는 코드를 바꾸지 않는다.** 분석 보고서와 개선안만 낸다.
2. 각 단계는 "계획 제시 → 창업자 승인 → 구현 → 테스트 → 보고" 순서로 진행한다. 승인 없이 다음 단계로 넘어가지 않는다.
3. 한 번에 한 화면(또는 한 기능)만 바꾼다. 트랙 A와 트랙 B를 한 커밋에 섞지 않는다.
4. 창업자는 비개발자다. 보고는 쉬운 한국어로, 전문 용어에는 짧은 설명을 붙인다.

### 0-2. 보존해야 하는 것
- 기능: 회원가입·이메일 인증·로그인·비밀번호 재설정·탈퇴, 호스트 신청·심사, 클래스 작성·검수·공개, 일정·정원, 신청·테스트 결제·취소·환불, 호스트 일정 취소, 알림, 관리자(2단계 인증·역할·감사 기록)
- 라우트: `/`, `/meetups`, `/meetups/[id]`, `/hosts/[id]`, `/me/*`, `/host/*`, `/admin/*`, `/checkout/*`, `/auth/*`, `/login`, `/signup` 등 **기존 주소는 바꾸지 않는다.** 새 이름이 필요하면(예: `/classes`, `/experts`) 기존 주소를 유지한 채 추가하거나 리디렉트한다.
- HTTP 상태: 권한 없음 403, 없는 페이지 404 (proxy.ts의 처리 유지)
- 테스트에서 쓰는 `data-testid` 이름. 바꿔야 하면 테스트도 같은 커밋에서 고친다.
- 디자인을 바꿔도 **보안 검사·테스트를 약하게 만들거나 지우지 않는다.**

### 0-3. DB 변경 규칙
- 기존 테이블·열·함수는 지우거나 이름을 바꾸지 않는다.
- 새 기능에 DB 변경이 꼭 필요하면 **추가만 하는 새 마이그레이션**으로 제안하고, 창업자 승인 후 만든다. 새 테이블은 RLS(행 단위 권한)와 pgTAP 테스트를 함께 만든다.
- 스테이징 DB 반영은 GitHub의 승인 절차(`Staging deploy & verify` 워크플로)로만 한다.

### 0-4. 안전 규칙 (이전부터 유지)
- 비밀번호·API 키·비밀키를 채팅·코드·로그에 남기지 않는다.
- 실결제·실제 환불·운영 DB 변경·운영 배포를 하지 않는다. (실결제·운영 배포는 계속 잠금)
- 실제로 실행하지 않은 배포·테스트를 성공했다고 보고하지 않는다.
- 테스트 계정과 감사 기록을 지우지 않는다.
- 샘플 데이터는 스테이징·로컬에만, `is_sample = true` + 화면에 "샘플" 표시.

### 0-5. 기술 규칙
- 스택 유지: Next.js 16(App Router) · TypeScript · Tailwind v4 · 직접 구성한 shadcn 스타일 컴포넌트 · Supabase · Vercel.
- **이 Next.js는 학습 데이터와 다르다.** 코드를 쓰기 전에 `node_modules/next/dist/docs/`의 해당 안내를 읽는다 (AGENTS.md).
- 새 라이브러리는 꼭 필요할 때만, 이유와 함께 제안 후 추가한다. (애니메이션 라이브러리 대신 CSS 우선)
- 색·글꼴은 `src/app/globals.css`의 디자인 토큰으로만 관리한다. 컴포넌트에 색 코드를 직접 쓰지 않는다.
- 브랜드명은 아직 가칭이다. 이름·문구는 `src/config/brand.ts` 한 곳에서 바꾼다.

### 0-6. 완료 기준 (매 단계)
`npm run check`(린트·타입·단위) · `npm run test:db` · `npm run test:integration` · `npm run build` 후 `npx playwright test` · `npm run scan:bundle` 모두 통과 + 모바일(390px)·데스크톱(1280px) 스크린샷 비교를 보고에 첨부.

## 1. 현재 상태 요약 (분석의 출발점 — 0단계에서 다시 확인할 것)

- 포지셔닝: 경력 심사를 거친 전문가의 **소수 정예 오프라인 클래스**. 메인 문구 "검증된 전문가에게, 소수 정예로 배우는 시간" (`src/config/brand.ts`)
- 카테고리(DB `categories`): 사진·영상(photo), 드로잉·공예(art), 악기·보컬(music), 커피·티·향(coffee), 요리·베이킹(cooking), 글쓰기(writing), 커리어·실무(career), 자세·운동(wellness). 친목형은 비활성(데이터 보존, DB 트리거가 새 등록 차단). 와인·주류는 법률 검토 전 잠금.
- 호스트 정보: 이름, 한 줄 소개, 소개, 전문 분야, 인스타그램 아이디, 경력(필수), 자격·수상, 포트폴리오 링크(https), 가르친 경험
- 클래스 정보: 제목, 요약, 소개, 가격, 1회 신청 인원(1~4), 난이도, 수업 후 할 수 있는 것, 재료·도구 안내, 진행 순서, 추천 대상, 준비물, 참여 조건, 환불 안내, 회차(일시·동네·장소·정원)
- **사진 기능이 없다.** `meetups.cover_image_url` 열은 있지만 화면에서 쓰지 않고, 이미지 업로드·저장소(Supabase Storage)도 아직 없다. 지금 표지는 카테고리 색으로 만든 "잡지형 표지"(`editorial-cover.tsx`)다.
- 후기·별점·결과물·찜·팔로우·검색·쿠폰·정산 화면: 없음
- 디자인 토큰: 오프화이트 배경 + 잉크색 + 테라코타 포인트, Pretendard + Noto Serif KR, 다크 모드 있음
- 스테이징: "클래스 중심 전환"까지 반영·자동 검증 완료 (2026-11-04, run #6). 리뉴얼은 이 상태에서 시작한다.

## 3. 트랙 A — 웹사이트 UI/UX 리뉴얼 (기능·DB는 그대로)

### A-1. 브랜드 방향
- 영문 메시지: **"Learn from people worth learning from."**
- 느낌: 절제된 프리미엄 라이프스타일 브랜드 + 독립 매거진 같은 에디토리얼 레이아웃. **특정 사이트를 베끼지 않는다.**
- "흔한 모임·이벤트 예약 사이트"처럼 보이지 않게 한다. (비교 대상: 문토=취향 소셜, 프립=액티비티, 동행클럽=시즌제 커뮤니티)

### A-2. 디자인 시스템 (먼저 정리하고 화면에 적용)
- 색 (토큰으로 등록)
  - Warm Ivory `#F5F2EB` (배경) · Charcoal `#252522` (글자·주요 버튼) · White `#FFFFFF` (면) · Muted Gray `#8A8881` (보조)
  - ⚠ Muted Gray는 아이보리 위에서 글자 대비가 약 3:1로 본문용 기준(4.5:1)에 못 미친다. **큰 글자·장식에만 쓰고, 작은 보조 글자는 더 진한 회색 토큰을 따로 만든다.**
  - 기존 테라코타 포인트는 유지 여부를 제안한다 (Originals 표시 등 한 가지 용도로만 쓰는 안 권장).
  - 다크 모드는 유지하되 같은 원칙으로 토큰을 다시 맞춘다.
- 글꼴: 기존 Pretendard(본문) + Noto Serif KR(제목) 유지. 영문 라벨용 글꼴 추가는 제안만.
- 원칙: 큰 이미지, 넉넉한 여백, 카드 테두리·둥근 모서리 최소화, 그라데이션·장식 아이콘 지양, 절제된 움직임(사용자가 "움직임 줄이기"를 켜면 끔), 모바일 우선.
- 공통 컴포넌트를 먼저 정리: 버튼, 링크, 섹션 제목(영문 라벨 + 한글 제목), 클래스 카드, 전문가 카드, 정보 목록, 배지(샘플·Originals·난이도), 빈 화면 안내.

### A-3. 사진 문제 (먼저 결정해야 함)
리뉴얼 효과의 대부분은 사진에서 나오는데, 지금은 사진 기능이 없다. 0단계 보고에서 아래 선택지를 비교해 제안한다.
1. 사진 없이도 완성도 있게: 잡지형 표지를 더 다듬고 타이포그래피 중심으로 설계 (DB 변경 없음)
2. 관리자만 사진 주소 입력: 기존 `cover_image_url` 활용 (DB 변경 없음, 사진 보관 위치 필요)
3. 호스트가 직접 업로드: Supabase Storage + 용량·형식 제한 + 권한 정책 (인프라 추가, 승인 필요)
- 규칙: 실제 사람처럼 보이는 AI 생성 사진이나 출처 불명 사진을 실제 수업·강사처럼 쓰지 않는다. 출시 전 화면의 예시 사진은 "샘플" 표시.
- 사진은 `next/image`로 최적화하고, 대체 텍스트를 필수로 한다.

### A-4. 홈 (`/`)

| 2 | 히어로: "좋아하는 것을 더 깊게. 전문가와 함께하는 시간." / 서브 "검증된 전문가에게 배우는 소수 정예 오프라인 클래스." / 버튼 EXPLORE CLASSES | 가능 | 문구는 brand.ts에. 사진 없으면 타이포그래피형 |

| 7 | 전문가 지원 유도: "당신의 전문성을 새로운 경험으로 만들어 보세요." → `/host/apply` | 가능 | |

### A-5. 클래스 카드
표시: 대표 이미지(또는 표지) · 제목 · 강사 이름 · 카테고리 · **소요 시간(가장 가까운 회차의 시작~끝으로 계산)** · 가격 · 남은 자리/정원 · 난이도. 한 화면에 너무 많이 보이지 않게(모바일 1열, 데스크톱 2~3열).

### A-6. 클래스 상세 (`/meetups/[id]`) — "교육 상품" 페이지로
권장 순서 (괄호 안은 이미 있는 데이터):
1. 대표 이미지·제목·요약·난이도 배지
2. **WHO WILL TEACH YOU** — 강사 (이름·한 줄 소개·경력·자격·포트폴리오)
3. **WHAT YOU WILL LEARN** — 수업 후 할 수 있는 것 (`learning_outcomes`)
4. **WHAT YOU WILL CREATE** — 가져가는 결과물 → 지금은 별도 칸이 없다. 1단계에선 "재료·도구 안내"와 학습 결과로 표현하고, 별도 칸(`result_description`)이 필요하면 **추가 마이그레이션으로 제안**
5. 커리큘럼 (`agenda`)
6. 진행 방식: 수업 방식(실습/현장/강의), 정원, **개인별 피드백 여부** → 피드백 여부 칸도 없다. 필요하면 위와 함께 제안
7. 추천 대상·준비물·참여 조건
8. 후기·결과물 → **데이터 생길 때까지 숨김**
9. 일정·장소(동네만, 상세 주소는 확정 후)·시간·가격·신청 (`booking-form`은 동작 그대로, 모양만)
10. 취소·환불 안내
11. 모바일 하단 고정 신청 버튼 (이미 있음, 디자인만 개선)
- 신청·결제·취소 흐름과 상태 코드(404 등)는 바꾸지 않는다.

### A-7. 전문가 페이지 (`/hosts/[id]`)
"판매자"가 아니라 브랜드의 핵심 인물로: 큰 이름·한 줄 소개, 경력·자격·가르친 경험, 포트폴리오, 인스타그램, 진행 중 클래스. 전문가 목록 페이지(`/experts` 또는 기존 주소 확장)는 새로 추가 제안.

### A-8. 그 밖의 화면
목록(`/meetups`), 로그인·가입, 마이페이지, 호스트·관리자 화면은 **새 디자인 토큰만 적용**하고 구조는 유지한다. 관리자 화면은 마지막 순서.

### 트랙 A 구현 순서 (각각 별도 승인)
A0 분석 보고 → A1 디자인 시스템(토큰·공통 컴포넌트) → A2 홈 → A3 클래스 상세 → A4 전문가 페이지·목록 → A5 나머지 화면 토큰 적용

## 4. 트랙 B — 인플루언서·크리에이터를 강사로 (사업 모델 확장)

> 트랙 B는 **기획·검증이 먼저**이고 개발은 그다음이다. 아래 B-1~B-3은 문서·운영으로 시작하고, 개발이 필요한 항목은 "개발 후보"로 따로 정리한다.

### B-1. 핵심 아이디어
"온라인에서 콘텐츠로 지식을 나누던 크리에이터가 오프라인에서 직접 가르치도록, 기획부터 모집·운영까지 Gathering이 돕는다."
→ 크리에이터의 전문성·콘텐츠·팔로워·개인 브랜드를 소수 정예 클래스 상품으로 바꾼다.

### B-2. 모집 기준
- **팔로워 수보다 가르치는 능력.** 팔로워가 많아도 교육 능력이 부족하면 선정하지 않는다.
- 평가: 실제 전문성 / 가르치는 능력(시범 수업 또는 기존 강의 이력) / 콘텐츠 품질 / 팔로워 참여도 / 오프라인 진행 적합성
- 팔로워 참여도는 **크리에이터가 직접 제출한 자료 + 운영팀 수동 확인**으로 본다. 인스타그램 자동 수집(스크래핑)은 하지 않는다 (이용약관 위반 소지).
- 1차 분야: 지금 열린 카테고리 안에서 시작 (사진·영상, 드로잉·공예, 악기·보컬, 커피·티·향, 요리·베이킹, 글쓰기, 커리어·실무, 자세·운동)
- 추가 검토 분야 (바로 열지 않음):
  - 뷰티·스타일링, 패션: 새 카테고리 추가 필요 (창업자 승인)
  - 운동·피트니스: 부상 위험 → 안전 고지·보험 검토 후
  - 와인·칵테일: 주류 잠금 유지 (법률 검토 완료 전 불가)

### B-3. 크리에이터에게 주는 가치 (운영 서비스)
클래스 기획·커리큘럼 → 가격·정원 설정 → 상세페이지 제작 → 예약·결제 → 모집 지원 → 장소 섭외 → 현장 운영 → 후기·결과물 관리 → 재수강 고객 확보
- 처음엔 **사람(운영팀)이 직접** 해 주고, 반복되는 일만 나중에 기능으로 만든다.

### B-4. 상품 형태 (아이디어)
| 상품 | 설명 | 개발 필요 |
|---|---|---|
| **첫 오프라인 클래스 런칭 대행** | "당신의 전문성을 오프라인 클래스로 만들어 드립니다." 크리에이터는 콘텐츠·전문성, Gathering은 상품화·운영 | 없음 (운영으로 시작) |
| **GATHERING ORIGINALS** | Gathering이 직접 기획·섭외하는 독점 클래스. 홈에서 일반 클래스와 구분 | `meetups`에 "Originals 여부" 표시 열 추가(마이그레이션, 승인 필요) |
| **팔로워 전용 프라이빗 클래스** | 크리에이터 팔로워 중 소수만, 높은 가격·직접 피드백 | 인스타그램 팔로워 여부는 확인할 수 없음 → **초대 링크/초대 코드로만 신청 가능한 비공개 클래스**로 구현 (DB 추가 필요) |
| **콜라보 클래스** | 두 분야 크리에이터가 함께 (사진×스타일링, 바리스타×디저트 등) | 지금은 클래스당 호스트 1명 구조 → 공동 호스트·수익 분배 설계 필요. **후순위** |

### B-5. 수익 배분 (가설 — 확정 아님)
- 기존 설계의 등급 수수료(신규 30%·성장 25%·우수 20%·핵심 파트너 15%)와 아래 크리에이터 가설을 **하나의 체계로 통합**해 제안한다.
  - 일반 강사 20~25% / Gathering이 섭외·운영 지원한 크리에이터 25~30% / 크리에이터 자체 팬덤으로 모집 15~20% / 공동 기획·장소 제공 등은 별도 협의
- 수수료율은 코드에 고정하지 않는다. 관리자가 바꿀 수 있는 설정값 + 결제 시점 값 저장(스냅샷) 원칙을 따른다.
- 재료비·장소비·결제 수수료·환불 비용을 누가 부담하는지 먼저 정의한다.
- 크리에이터 "자체 모집" 여부를 구분하려면 **유입 경로 기록(추천 코드/링크)**이 필요하다 → 개발 후보.

### B-6. 꼭 지켜야 할 법·신뢰 항목 (출시 전 확인)
- **광고 표시**: Gathering이 대가(수익 배분 포함)를 주는 크리에이터가 SNS에서 클래스를 홍보하면 "광고/유료 협찬" 표시가 필요할 수 있다 (공정위 추천·보증 심사지침). 크리에이터 계약·가이드에 넣는다.
- 통신판매중개업자 고지, 강사(크리에이터) 소득 원천징수·사업자 여부, 환불 규정 법률 검토, 운동 클래스 안전·보험, 주류 잠금.
- 크리에이터 개인정보(연락처·정산 계좌)는 공개 프로필과 분리해 보관.

### B-7. 첫 실험 (개발보다 먼저)
**크리에이터 5명 파일럿**: 분야를 섞고, 팔로워가 적어도 실력 있는 사람을 1~2명 포함. 각자 클래스 1개 개설.
비교 지표: 상세페이지 방문 → 신청 전환율, 실제 참석률, 만족도, 재수강 의사, 크리에이터 재개설 의사, 크리에이터 채널에서 온 신청 비율.
→ 지금 사이트로 측정 가능한 것(신청·취소 수)과 추가가 필요한 것(유입 경로, 참석 체크, 만족도 설문)을 0단계 보고에 정리한다.
→ 실제 결제는 아직 잠겨 있으므로, 파일럿을 유료로 하려면 **토스페이먼츠 실결제 전환(계약·정산 구조 확인·창업자 승인)**이 먼저다.

## 5. 향후 개발 후보 (지금 만들지 않음 — 우선순위만 제안)

0단계 보고에서 각 항목의 가치·난이도·DB 변경 여부를 표로 정리한다.

- 강사·크리에이터: 포트폴리오 강화, 클래스 관리 대시보드(일부 있음), 참가자 관리(있음), 정산 내역, 후기 관리, **유입 경로(추천 링크) 분석**, 클래스별 매출
- 운영: Originals 표시, 초대 전용 클래스, 출석 체크, 만족도 설문, 크리에이터 지원서 단계(기존 호스트 신청 확장)
