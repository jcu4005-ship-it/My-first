# 법률·운영 정책 시스템 (사업자 정보 · 이용약관 · 개인정보 처리방침 · 취소·환불 규정)

> 2026-11-26 구현. **모든 문구는 초안이며 법률 검토 전입니다.** 사업자 정보는 임의로 만들지 않았고 입력 자리(placeholder)만 있습니다.

## 1. 어디에 무엇이 있나

| 항목 | 화면 | 내용을 고치는 곳 |
|---|---|---|
| 사업자 정보 | 모든 공개 화면 바닥글, 이용약관 13조 | `src/config/business.ts` (값을 채움) |
| 이용약관 | `/terms` (독립 페이지) | `src/app/terms/page.tsx` |
| 개인정보 처리방침 | `/privacy` (독립 페이지) | `src/app/privacy/page.tsx` (수집 항목·외부 서비스 표) |
| 취소·환불 규정 | `/refund`, 프로그램 상세, 결제 화면 | 문구 `src/app/refund/page.tsx`, **비율 숫자 `src/lib/payments/refund-policy.ts`**(DB 계산과 같은 규칙) |
| 개정일·시행일·버전·이력 | 각 문서 맨 위 | `src/config/legal.ts` |
| 가입 시 필수 동의 | 회원가입 화면 (이용약관 · 개인정보 · 만 14세 필수 / 마케팅 선택, 각 "보기" 링크) | 동의 이력은 DB `legal_consents`에 버전과 함께 저장 |

- **바닥글**: 홈·프로그램·크리에이터·로그인·가입·결제·1:1 문의 화면에 표시. (관리자·호스트 관리 화면은 내부 화면이라 제외)
- **결제 직전**: 결제 화면에 그 프로그램의 환불 단계를 날짜와 함께, "크리에이터가 취소하면 전액 환불" 안내, 취소·환불 정책 전문·이용약관 링크
- **참가자 취소 vs 크리에이터 취소**: 약관 7조, 환불 정책 1·2조, 결제·상세·홈 화면에서 구분해서 안내. 크리에이터가 일정을 취소하면 날짜와 관계없이 전액 환불(DB 함수 `host_cancel_session`이 처리)

## 2. 대표가 직접 입력해야 하는 정보 (`src/config/business.ts`)

사업자등록증·통신판매업 신고증에 적힌 그대로 입력하세요. 비어 있는 동안 화면에는 `[… 입력 필요]`가 보입니다.

| 항목 | 어디서 확인 | 비고 |
|---|---|---|
| 상호 (`companyName`) | 사업자등록증 | "ROUNDI (가칭)" 표기도 이 값으로 교체 |
| 대표자 (`representative`) | 사업자등록증 | |
| 사업자등록번호 (`businessNumber`) | 사업자등록증 | 000-00-00000 |
| 통신판매업 신고번호 (`mailOrderNumber`) | 신고증 (구청, 신고 후 발급) | PG 계약·구매안전서비스 확인증 필요 |
| 사업장 주소 (`address`) | 사업자등록증 | 자택이면 공개 동의 확인(대표 확인: 공개 괜찮음) |
| 고객센터 전화 (`csPhone`) / 이메일 (`csEmail`) / 운영시간 (`csHours`) | 직접 정함 | |
| 개인정보 보호책임자 (`privacyOfficer`) | 직접 지정 | 이름·연락처 |
| 통신판매 관련 고지 (`intermediaryNotice`) | **법률 검토 후 확정한 문구** | 플랫폼의 법적 지위를 임의로 쓰지 않음 |
| 호스팅 서비스 제공 (`hosting`) | 이미 적어 둠 (Vercel · Supabase) | 정확한 법인명은 확인 후 확정 |

다 채우면 바닥글의 "입력 필요" 안내가 자동으로 사라집니다. 비어 있는 항목은 `missingBusinessInfo()`로 확인할 수 있어요.

## 3. 법률 검토가 필요한 문구 (화면에 "법률 검토 필요" 표시)

초안인 동안(`isDraft: true`)에만 각 조항 아래에 주황색 표시가 보이고, 확정하면 자동으로 사라집니다.

- **약관**: 플랫폼의 법적 지위(통신판매중개 해당 여부)와 책임 범위 · 면책/책임 제한 · 약관 변경 공지 기간과 "계속 이용 시 동의 간주" · 만 14세 미만 가입 차단 방식 · 결제 주체/결제대행 구조 · 정산·세금 처리 · 관할·분쟁 해결
- **개인정보 처리방침**: 항목별 보유 기간과 파기 방법(지원서·인터뷰 기록 포함, 자동 파기는 미구현) · 국외 이전(Supabase·Vercel 서버 위치) · 위탁/제3자 제공 구분 · 결제대행사·메일 발송 업체·AI 분석 도구 확정 후 고지/동의 · 개인정보 보호책임자 지정
- **취소·환불 규정**: 환불 비율의 법령·소비자분쟁해결기준 적합성 · 결제수단별 환불 소요 기간(임시 "영업일 3~7일") · 부분 환불 시 PG 수수료 처리

## 4. 확정 후 절차 (개정일·시행일)

1. 법률 검토를 거친 문구로 페이지를 고칩니다.
2. `src/config/legal.ts`에서 해당 문서: `isDraft: false`, `version` 새 값(예: `v1.0`), `revisedAt`·`effectiveAt`을 `YYYY-MM-DD`로 입력합니다. (확정 전에는 `null` — 임의 날짜 금지)
3. 이후 개정할 때는 현재 값을 `history` 맨 위로 옮기고 새 값을 적습니다. 화면에 "이전 버전 보기"가 자동으로 생깁니다.
4. `version`이 바뀌면 신규 가입자의 동의 이력에 새 버전이 저장됩니다. 기존 회원 재동의 절차는 법률 검토 때 정합니다.
5. 시행일 전에 사이트 공지(약관 4조: 시행일 7일 전, 불리한 변경은 더 길게 — 확인 필요)

## 5. 관리자 페이지에서 정책 내용을 수정할 수 있게 할까? (검토 의견)

**지금은 코드 방식을 유지**하고, 아래 조건이 되면 DB 방식으로 옮기는 것을 권합니다.

| | 코드에서 관리 (현재) | DB 문서 + 관리자 편집 |
|---|---|---|
| 장점 | 변경 이력이 git에 남고 리뷰·테스트가 쉬움, 구현 단순, 잘못 고칠 위험이 작음 | 대표가 직접 수정·게시, 개발 없이 개정 가능 |
| 단점 | 수정마다 개발자(저)가 필요 | 법적 문서를 쉽게 바꿀 수 있어 사고 위험, 구조·권한·감사 설계 필요, 가입 동의 버전과의 연결 관리 |
| 적합 시기 | **법률 검토 전·초안 단계 (지금)** | 법률 검토 확정 후, 문구가 자주 바뀔 때 |

DB 방식으로 만든다면 권장 구조: `legal_documents`(종류, 버전, 제목, 본문(마크다운), 상태 draft/published, 개정일, 시행일, 작성자) + 게시는 **관리자 2단계 인증 + 사유 필수 + 감사 기록**, 게시된 버전은 수정 불가(새 버전으로만 개정), 사이트는 `시행일이 지난 최신 published`를 표시, 가입 동의는 그 버전 ID를 기록. **사업자 정보는 값이 적어 먼저 관리자 "운영 설정" 화면(`/admin/launch`)에 입력칸으로 옮기는 안**도 가능합니다 (필요하면 요청해 주세요).

## 6. 점검표 (수집·외부 서비스가 바뀔 때)
- [ ] 새로운 개인정보 항목을 받는 기능을 만들었다 → `/privacy` 수집 항목 표와 보유 기간 추가
- [ ] 새 외부 서비스(결제, 메일, 분석, AI 등)를 연결했다 → `/privacy` 외부 서비스 표 추가, 필요하면 동의 문구 수정
- [ ] 환불 비율을 바꿨다 → `refund-policy.ts`와 DB 함수(`private.refund_percent`)를 함께, 화면 문구 확인
- [ ] 문구를 실질적으로 바꿨다 → `legal.ts` 버전·개정일·시행일·이력
